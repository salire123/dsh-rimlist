导出作用Python 类比

inject声明"我需要宿主提供 tools 服务"。DSH 在调用 apply 前会保证这个服务可用有点像 __init__.py 里声明的依赖，或者是依赖注入框架的注解

ctx 是什么

它是一个"服务容器"。全文出现了这么几种用法，看到就知道在干嘛：

代码含义
ctx.get('webServer')取出 HTTP 服务（拿到才能注册路由）。没装就是 undefined
ctx.get('timer')取出定时器服务（用来重试）
ctx.tools.register(tool)注册一个 AI 工具
ctx.inject(['sidebarRightTabs'], cb)（前端）等某个服务就绪后执行回调

为什么用 ctx.get 而不是直接 import

因为插件和宿主是分开打包的。插件不能 import 宿主代码，只能从 ctx 里"要"。这样宿主可以换实现，插件不用改。

启动流程，按执行顺序

apply(ctx) 被 DSH 调用 │ ├─ ① 算出数据目录 dshHome/rimlist ├─ ② createService({ dataDir, log }) ← 创建服务对象（同步、很快） ├─ ③ service.init() ← 不 await！后台跑 ← 读设置、扫描磁盘、加载规则库 ├─ ④ 定义 httpHandler ← 只是个函数，还没生效 ├─ ⑤ registerRoute() ← 真正把 /api/rimlist 挂上去 ├─ ⑥ 如果没拿到 webServer，开一个定时器重试 ├─ ⑦ 定义 31 个 AI 工具 ├─ ⑧ ctx.tools.register(tool) × 31 └─ ⑨ return 一个清理函数 ← 插件卸载时调用
注意 ③ 里的"不 await"

扫描磁盘可能要几秒钟（几百个 mod 文件夹）。如果这里 await，整个 DSH 启动就会卡住。所以它在后台跑，界面上先显示"正在扫描 RimWorld…"。这是一个很典型的性能取舍。

数据目录~/.dsh/rimlist。注释解释了原因：游戏装在电脑上，是全局的，不属于某个工作区，所以数据不放在工作区目录里。

④ 一个手写的 HTTP 处理器

这是后端唯一对外的接口。整个项目就靠它服务前端和 AI 工具。

index.js:36-51
const MAX_BODY = 4 * 1024 * 1024
const sendJson = (res, status, value) => {
  res.writeHead(status, { 'content-type': 'application/json; charset=utf-8' })
  res.end(JSON.stringify(value))
}
const sameOrigin = (req) => {
  const origin = req.headers?.origin
  const host = req.headers?.host
  if (!origin || !host) return true
  try {
    return new URL(origin).host === host
  } catch {
    return false
  }
}

没有用 Express 之类的框架，直接操作 Node 原生的 req / res。两个函数都很小：

  • sendJson：设状态码和 content-type，序列化后发送。等价于 Flask 的 return jsonify(x), status。
  • sameOrigin：安全检查。只允许同一个站点发来的请求，防止别的网页偷偷调用你的本地接口改 mod 顺序。
sameOrigin 的逻辑值得细看

if (!origin || !host) return true —— 没有 Origin 头就放行。因为非浏览器客户端（比如 curl、DSH 自己的内部调用）不会带这个头。浏览器跨站请求一定会带，所以这道防线只挡浏览器。

主处理函数

index.js:52-84
const httpHandler = async (req, res) => {
  try {
    const url = new URL(req.url, 'http://x')
    // Preview images: GET /api/rimlist/preview?id=<packageId>
    if (req.method === 'GET' && url.pathname.endsWith('/preview')) {
      const p = await service.dispatch('previewPath', { packageId: url.searchParams.get('id') || '' })
      if (!p) return sendJson(res, 404, { error: 'no preview' })
      const s = await stat(p)
      res.writeHead(200, { 'content-type': p.endsWith('.jpg') ? 'image/jpeg' : 'image/png', ... })
      createReadStream(p).pipe(res)
      return
    }
    if (req.method !== 'POST') return sendJson(res, 405, { error: 'Method not allowed' })
    if (!sameOrigin(req)) return sendJson(res, 403, { error: 'Cross-origin request denied' })
    const ct = String(req.headers['content-type'] || '').toLowerCase()
    if (!ct.startsWith('application/json')) return sendJson(res, 415, { error: 'Expected application/json' })
    const chunks = []
    let size = 0
    for await (const chunk of req) {
      size += chunk.length
      if (size > MAX_BODY) return sendJson(res, 413, { error: 'Request body too large' })
      chunks.push(chunk)
    }
    const body = chunks.length ? JSON.parse(Buffer.concat(chunks).toString('utf8')) : {}
    const method = typeof body.method === 'string' ? body.method : 'snapshot'
    const args = isObj(body.args) ? body.args : {}
    const result = await service.dispatch(method, args)
    return sendJson(res, 200, { ok: true, result })
  } catch (err) {
    const status = err instanceof SyntaxError ? 400 : 500
    return sendJson(res, status, { ok: false, error: String((err && err.message) || err) })
  }
}

这个函数值得逐段读，因为它包含了后端所有的"防御性编程"套路：

  1. 先处理特例：预览图
    GET /api/rimlist/preview?id=xxx 直接返回图片文件流。这是唯一的 GET 接口，其他的都是 POST。
  2. 三道校验，每道都提前 return
    不是 POST → 405；跨源 → 403；不是 JSON → 415。错误在最早的地方返回，后面的代码就不用操心了。这个风格叫"guard clause"（卫语句），比层层嵌套 if 好读得多。
  3. 手动读 body，边读边限长
    for await (const chunk of req) 一块块读（Node 的流）。每读到一块就累加长度，超过 4 MB 立刻返回 413。不是读完才检查 —— 否则恶意请求可以用 1 GB 打爆内存。
  4. 容错解析
    body.method 不是字符串就用 'snapshot'（默认就是"给我全部状态"）；body.args 不是对象就空对象。前端传错也不会崩。
  5. 一行分发
    service.dispatch(method, args) —— 这里没有 if/else 大列表，因为真正的分派在 service.js 里（第 6 页）。入口只负责 HTTP，业务逻辑全在 service。
  6. 统一异常出口
    整个函数体包在 try/catch 里。SyntaxError（JSON 解析失败）返回 400，其他都返回 500。永远给前端一个 JSON，不会挂在那里不响应。
第 3 步的一个语法点

for await (const chunk of req) —— 这是"异步迭代"，Python 里对应 async for chunk in req。只用于流这类"数据会陆续到来"的对象。

⑤ 注册路由，以及为什么需要重试

index.js:86-113
const routeState = { registered: false, timer: null, dispose: null, disposed: false, attempts: 0 }
const registerRoute = () => {
  if (routeState.registered || routeState.disposed) return
  const webServer = ctx.get('webServer')
  if (webServer === undefined) return
  try {
    const dispose = webServer.register({ kind: 'prefix', path: '/api/rimlist', handler: httpHandler })
    routeState.dispose = typeof dispose === 'function' ? dispose : null
    routeState.registered = true
    log('/api/rimlist route registered')
  } catch (err) {
    log('route registration failed: ' + ((err && err.message) || err))
  }
}
registerRoute()
if (!routeState.registered) {
  const timer = ctx.get('timer')
  if (timer) {
    routeState.timer = timer.interval(() => {
      routeState.attempts++
      registerRoute()
      if (routeState.registered || routeState.attempts >= 40) {
        if (routeState.timer) routeState.timer()
        routeState.timer = null
      }
    }, 500)
  }
}

为什么不能直接注册？因为 DSH 加载插件的顺序不保证 webServer 已经就绪。可能插件先加载，HTTP 服务器后起来。所以：

  1. 先试一次（registerRoute()）
  2. 没成功就每 500 ms 再试，最多 40 次（20 秒）
  3. 成功或超时就停掉定时器

这 5 个字段的 routeState 是在管理这个"重试状态机"。写得很啰嗦但很稳。

为什么要检查 disposed

因为定时器可能在插件卸载之后才触发。那时再去注册路由就会出错。disposed 标志位让回调能知道"我已经死了，别干活"。

每个工具都是这个形状，五个字段：

字段作用给谁看
name工具名，AI 用它调用。都以 rimlist_ 开头AI
description一段英文说明"这个工具干什么、什么时候该用"AI 看这个决定要不要用

为什么要分开？因为数据要能再次被程序处理（存文件、给别的工具用），而文本只给人看。混在一起就麻烦了。这是个很好的设计习惯。

run() 和 textOut() 两个辅助函数

index.js:116-128
const textOut = (fn) => ({
  schema: { type: 'object', additionalProperties: true },
  render: (args, value) => [{ type: 'text', text: fn(value) }],
})
const run = async (method, args) => {
  try {
    // JSON round-trip: drops undefined / Sets / Maps so the host gets lossless JSON.
    return JSON.parse(JSON.stringify({ ok: true, ...(await wrapResult(await service.dispatch(method, args))) }))
  } catch (err) {
    return { ok: false, error: String((err && err.message) || err) }
  }
}
const wrapResult = async (r) => (isObj(r) ? r : { result: r })

这两个是所有工具共用的样板，理解它们就等于理解了 31 个工具：

textOut(fn)收一个格式化函数，返回工具的输出描述对象。每个工具定义里那一大段 textOut((v) => {...}) 就是在写这个 fn。
run(method, args)调 service 并把结果包装成 { ok: true, ...结果 }。永远不抛异常 —— 出错就返回 { ok: false, error }。这样 AI 能读懂错误。
wrapResult如果 service 返回的不是对象（比如一个数组），包成 { result: [...] }，保证展开运算符 ... 不出错。
JSON round-trip丢掉 undefined、Map、Set。因为工具结果最终要变成 JSON 文本传给 AI，这些东西没法序列化。

apply 返回一个清理函数。DSH 卸载插件（或退出）时会调用它，把定时器停掉、路由撤掉。这是 JavaScript 里"资源释放"的标准模式 —— 相当于 Python 的 __exit__ 或 atexit，但更局部。

为什么返回函数而不是用 try/finally

因为插件的生命周期比一次函数调用长得多。apply 早返回了，插件还在跑。只能约定"你返回一个函数，我到时候调它"。
