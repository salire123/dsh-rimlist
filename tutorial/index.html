RimWorld Mod 管理器 · 源码阅读课

读懂 rimlist 这是一个 DeepSeek Harness 的插件，用 JavaScript 写的。你懂一点 Python，但没写过 JS —— 这份导读就是为你准备的。

先说结论：这个项目不需要你"通读全部 9000 行"。它有 30 多个文件，但真正的主干只有 6 个。读懂这 6 个，你就能自己改功能了。

这份导读的顺序就是读代码的顺序：先补 JS 语法（第 1 页），再从入口一路往下走（第 2–6 页），最后看界面怎么画出来（第 7 页）。

这个项目到底在干什么

RimWorld 玩家装几十上百个 mod，游戏能不能跑起来，全看 加载顺序：A 必须在 B 前面，B 依赖 C，D 和 E 不能同时开……手排非常痛苦。

RimList 就是来解决这件事的。它做的事，用一句话说：

一句话

读一堆 XML（每个 mod 的 About.xml）→ 建成一张"谁必须在谁前面"的图 → 拓扑排序 → 把结果写回游戏的 ModsConfig.xml。

剩下的所有代码，都是这句话的配套：怎么找到 mod 文件夹、规则库从哪下载、界面上怎么拖拽、出错了怎么诊断、怎么把顺序分享给别人。

程序分成两半

打开仓库你立刻会看到一个分叉：src/host 和 src/client。这不是风格问题，是两个不同的运行环境。这是理解整个项目最重要的一件事。

host 后端 · Node.js

跑在电脑上（通过 DSH 主进程），能读文件、能起 HTTP 服务、能执行 git 命令。

负责：扫描磁盘、解析 XML、排序、诊断、写配置文件。

index.js + src/host/*.js

client 前端 · 浏览器

跑在网页里（DSH 的 Web 界面），不能碰文件系统，只能发网络请求。

负责：画界面、拖拽、点按钮 → 调后端。

src/client/*.jsx

两边唯一的联系方式是一个 HTTP 接口：

src/client/api.js（节选）
const res = await fetch('/api/rimlist', {
  method: 'POST',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({ method, args }),
})

前端把"我要做什么"打包成 { method: 'sortIds', args: {...} } 发过去，后端做完把 JSON 结果发回来。就这么简单 —— 前端永远不知道 ModsConfig.xml 在哪。

数据流全景
浏览器（src/client） store.js api('sortIds', { ids }) ← 用户点了「⇅ 排序」 │ │ POST /api/rimlist { method: 'sortIds', args: { ids } } ▼ index.js httpHandler() ← 校验同源、读 body、解析 JSON │ ▼ src/host/service.js methods.sortIds │ ├─ sortLoadOrder(keys, catalog, rules) ← src/host/sorter.js 真正的算法 └─ diagnose(...) ← 顺便算一下有没有问题 │ ▼ { ok: true, result: { order: [...] } } JSON 原路返回 │ ▼ store.js setDraft(r.order) ← 只是"草稿"，还没写盘！ 用户再点「保存到游戏」→ api('setActive') → writeConfig() → ModsConfig.xml（先备份）
注意最后两步是分开的

排序只改界面里的草稿，不写文件。只有点「保存到游戏」才真的写 ModsConfig.xml。所以你在界面上怎么折腾都不会弄坏游戏配置 —— 这对读代码也有用：写盘的地方只有一处。

dict / listObject / Array（还有 Map / Set）⭐
推导式.map() .filter() .reduce()⭐⭐
async / await几乎一模一样⭐⭐
模块与 importESM：export / import⭐⭐
类型注解没有（纯 JS），靠命名和注释—
闭包、装饰器闭包一样；装饰器 ≈ 高阶函数⭐⭐⭐
类与继承本项目基本不用 class，用工厂函数返回对象⭐⭐
异常 try/excepttry/catch，语义相同⭐

读代码前需要知道的 RimWorld 概念

不用会玩游戏，但这几个词会反复出现：

概念含义在代码里
packageIdmod 的全局唯一 ID，像 brrainz.harmony。RimWorld 认这个，不认文件夹名。m.key（永远小写）和 m.packageId（保留原样大小写）
About.xml每个 mod 必须有的一张名片：名字、作者、支持版本、加载顺序要求。src/host/xml.js 的 parseAbout()
ModsConfig.xml游戏记住"你启用了哪些 mod、按什么顺序"的文件。改这个文件就等于改加载顺序。buildModsConfig() 写它，parseModsConfig() 读它
loadAfterAbout.xml 里声明"我要在某 mod 之后加载"。mod.loadAfter
loadBottom / loadTop社区约定：置底（补丁类）和置顶（框架类）。规则库里的 loadBottom / loadTop
Core / DLC游戏本体（ludeon.rimworld）和官方资料片（Royalty、Ideology…）。永远排最前。CORE_ID、KNOWN_EXPANSIONS（scan.js）
Harmony几乎所有代码 mod 的前置库，必须比 Core 还早加载。sorter.js 里的 RS_TIER0 第一个就是它
创意工坊 / WorkshopSteam 的 mod 平台。mod 装在 steamapps/workshop/content/294100/。source: 'workshop'
大小写陷阱（提前剧透）

RimWorld 比较 packageId 时区分大小写，但它自己内部用的是小写。如果 ModsConfig.xml 里写了 Ludeon.RimWorld，游戏会显示成一个灰色的重复项。所以这份代码里到处都是 pid() 函数（把字符串转小写），m.key 永远是 pid(packageId)。第 3 页会细讲。
