前端 React 如果你只想改算法，这页可以跳过。但如果你想改界面，React 的三个概念必须先懂：组件、状态、渲染。

React 是什么，一句话

你写一个函数，输入是数据，输出是"界面长什么样"的描述。数据变了，React 自动重新调用你的函数，把界面更新掉。

你永远不写"找到那个 DOM 元素然后改它的文字"。你只描述"应该是什么样"，剩下的交给 React。这是和 jQuery 那类写法最根本的区别。

核心概念①：组件就是一个返回 JSX 的函数

src/client/columns.jsx:44-52
export function TagFilter({ allTags, tag, setTag, tagIndex }) {
  return (
    <select className="rl-select rl-tag-select" value={tag} onChange={(e) => setTag(e.target.value)} title={t('filterByTag')} disabled={!tagIndex}>
      <option value="">{tagIndex ? t('allTags') : t('tagsLoading')}</option>
      {allTags.map(([g, n]) => <option key={g} value={g}>{g} ({n})</option>)}
    </select>
  )
}

拆解：

函数名大写TagFilter —— React 约定：组件名必须大写开头。小写的会被当成普通 HTML 标签。
{ allTags, tag, ... }参数是一个对象，直接解构出各个"prop"（属性）。调用时是 <TagFilter allTags={x} tag={y} />。
返回 JSX外观像 HTML，实际是函数调用。注意 className、onChange。
{表达式}花括号里可以放任何 JS 表达式。{tagIndex ? ... : ...} 是三元，{allTags.map(...)} 是循环。

用 map 生成列表（React 里唯一的循环方式）

上面那个 {allTags.map(([g, n]) => <option key={g} ...>...</option>)} 值得单独讲：

{allTags.map(([g, n]) => <option key={g} value={g}>{g} ({n})</option>)}
(tag, count)allTags 是 [['工具', 12], ['界面', 5]] 这样的二元组数组。[g, n] 是数组解构。
key={g}必须有！React 用它识别"哪个元素是哪个"。没有 key 会警告，而且列表重排时可能出错。
没有 for 循环JSX 里不能写 for。只能用 .map()（返回数组）或 &&（条件渲染）。
和 Python 模板引擎的对比

Jinja2 里你会写 {% for tag, n in all_tags %}。React 因为就是 JS，所以直接用 .map() —— 没有额外的模板语法要学。

核心概念③：副作用（useEffect）

有些事不是"渲染界面"，而是"要做点什么"：发请求、设定时器、加事件监听。这些放进 useEffect。

src/client/store.js:22-36
const refresh = useCallback(async () => {
  try {
    const s = await api('snapshot')
    setSnap(s)
    setDiag(s.diagnostics)
    setError(null)
    return s
  } catch (e) {
    setError(e.message)
  }
}, [])

useEffect(() => {
  refresh()
}, [refresh])

结构是 useEffect(函数, 依赖数组)：

写法什么时候跑
useEffect(fn, [])只在第一次渲染后跑一次（相当于 init）
useEffect(fn, [a, b])a 或 b 变了就跑
useEffect(fn)每次渲染后都跑（很少用）
return () => {...}清理函数，组件卸载或下次跑之前调用

一个带清理的例子

src/client/app.jsx:71-80（轮询游戏是否在运行）
const [running, setRunning] = useState(false)
useEffect(() => {
  let alive = true
  const poll = () => api('gameStatus').then((r) => alive && setRunning(!!r?.running)).catch(() => {})
  poll()
  const id = setInterval(poll, 4000)
  return () => {
    alive = false
    clearInterval(id)
  }
}, [])
setInterval(poll, 4000)每 4 秒查一次游戏在不在跑。这样界面上"启动 / 停止"按钮能自动切换。
return () => {...}清理函数。组件被移除时必须停掉定时器，否则会一直跑（内存泄漏）。
alive 标志防止"请求发出去了，组件已经卸载了，回来时 setState 报错"。这是 React 里非常经典的坑，用闭包变量解决。
依赖数组的坑

上面那个 [] 意思是"永远不重跑"。如果写成 [running]，每次 running 变化都会重跑 —— 清掉旧定时器、建新的，而且 poll() 会立刻再发一次请求。依赖数组写错会导致无限循环。

如果漏了某个依赖，闭包会捕获旧的值（stale closure）。这是 React 最难 debug 的一类问题。

useCallback / useMemo 是干什么的

src/client/store.js:38（useMemo 的例子）
const catalog = useMemo(() => new Map((snap?.mods || []).map((m) => [m.key, m])), [snap])

建一个 Map 是 O(n)。如果每次渲染都重建，几百个 mod 就是几百次操作 × 每次键盘输入。所以用 useMemo 缓存：只有 snap 变了才重建。

Hook作用Python 类比
useMemo(fn, deps)缓存计算结果functools.lru_cache（按 deps 作 key）
useCallback(fn, deps)缓存函数本身（避免每次渲染都造新函数）没有直接对应
useRef(init)存一个"跨渲染保持，但改它不触发重画"的值可变的闭包变量
为什么 useCallback 在本项目里很重要

看 store.js:34：useEffect(() => { refresh() }, [refresh])。refresh 在依赖数组里！如果 refresh 每次渲染都是新函数，useEffect 每次都重跑，就无限发请求了。

所以 refresh 必须用 useCallback(..., []) 包住，保证引用稳定。这两个 Hook 是配套使用的。

    setOrder: (ids) => setDraft(ids),
    activate: (keys, index) => { ... },
    deactivate: (keys) => { ... },
    move: (key, to) => { ... },
    discard: () => setDraft(null),
    setOrderFromServer: async () => { setDraft(null); await refresh() },
    save: () => run(async () => { await api('setActive', { ids: active }); setDraft(null); await refresh() }, t('saved')),
    sort: () => run(async () => { ... }),
    rescan: () => run(async () => { ... }, ...),
    api: (method, args, okMsg) => run(() => api(method, args), okMsg),
    say,
  }

  return { snap, error, busy, toast, active, dirty, diag, catalog, actions }

整个前端只有这一个"状态中心"。所有组件从 useRimlist() 拿数据、调用 actions。

这个模式叫 "custom hook"

把一堆相关的 useState + useEffect + 操作函数打包成一个函数 useRimlist()，返回一个对象。组件里一行 const { snap, actions } = useRimlist() 就拿到全部能力和数据。

Python 里最接近的类比：一个带状态的控制器对象。但注意 —— 这不是 class，是每次渲染都重新执行的函数。useState 负责"把状态存在 React 那里，跨渲染保留"。

run() 这个包装器的价值

看看它统一处理了什么：

setBusy(true)所有按钮自动变灰（页面里到处 disabled={busy}）。用户不会重复点击。
try/catch任何 API 错误都变成一条 toast 提示，界面不会白屏。
finally成功失败都恢复 busy = false。不会卡在"永远加载中"。
throw e报完错还往上抛，调用方可以选择额外处理（比如 startGame 里额外 say('❌ ...')）。

如果没有这个包装，每个按钮都要写一遍 try/catch/setBusy/toast。现在只要 run(async () => {...})。

多选：这是前端最有含金量的逻辑

src/client/columns.jsx:109-120
const select = (key, e) => {
  if (e.shiftKey && selection.anchor) {
    const a = order.indexOf(selection.anchor)
    const b = order.indexOf(key)
    const [lo, hi] = a < b ? [a, b] : [b, a]
    setSelection({ keys: new Set(order.slice(lo, hi + 1)), anchor: selection.anchor, focus: key, side: 'active' })
  } else if (e.ctrlKey || e.metaKey) {
    const keys = new Set(selection.side === 'active' ? selection.keys : [])
    keys.has(key) ? keys.delete(key) : keys.add(key)
    setSelection({ keys, anchor: key, side: 'active' })
  } else setSelection({ keys: new Set([key]), anchor: key, side: 'active' })
}
按键行为实现
普通点击只选这一个new Set([key])
Shift + 点击从 anchor 到这里的一整段算 lo/hi 后 slice
Ctrl / Cmd切换这一个（加/减）has ? delete : add
三个细节
  1. anchor 和 keys 分开存。keys 是选中的集合，anchor 是"从哪开始算 Shift 范围"。没有 anchor 就没法做范围选择。
  2. 用 Set 而不是数组。因为要频繁 has / add / delete，Set 是 O(1)。
  3. metaKey = macOS 的 Cmd。写 e.ctrlKey || e.metaKey 才能跨平台。

onDrop: (e) => {

  }

它在处理一个经典难题：多选状态下拖动，插入位置怎么算？

为什么难

假设列表是 [A, B, C, D, E]，你选中了 [A, B]，想拖到 D 前面。目标索引是 3。

如果直接把 A、B 插到索引 3，结果会是 [C, D, A, B, E] —— 错了。因为你把 A、B 从前面抽走之后，后面的元素全都往前挪了 2 位，D 现在在索引 1 而不是 3。

所以要修正：idx - (被移走的、且在目标之前的元素个数)。这就是那一行的含义：

insertAt = idx - drag.keys.filter((k) => order.indexOf(k) < idx).length

在本例中：3 - 2 = 1。把 [A,B] 插到 [C,D,E] 的索引 1 → [C, A, B, D, E]。正确。

if (e.altKey && (e.key === 'ArrowUp' || e.key === 'ArrowDown') && selection.side === 'active' && selection.keys.size) {

  const sel = selection.keys

  for (const i of up ? idxs : idxs.reverse()) {

sel.has(k) ? i : -1选出所有被选中的下标。不用 filter + indexOf，一次遍历搞定。
边界检查已经到顶还要上移？直接 return。（idxs[0] === 0 表示最上面那个也被选中了。）
up ? idxs : idxs.reverse()关键！往下移必须从下往上处理，否则会互相踩踏。
举例：选中 [1,2] 往下移。正序：先换 1↔2（变成 2 在那个位置），再换 2↔3 —— 乱套了。倒序：先换 2↔3，再换 1↔2。正确。
;[a, b] = [b, a]交换两个元素。行首那个分号不能省！否则上一行的 const j = ... 会被解析成连续表达式（... i + 1;[...] 是数组字面量）。这是 JS 自动分号插入的坑。

数据怎么到前端：就那一个函数

src/client/api.js:1-16
export async function api(method, args = {}) {
  const res = await fetch('/api/rimlist', {
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ method, args }),
  })
  let body
  try {
    body = await res.json()
  } catch {
    throw new Error(`rimlist: bad response (${res.status})`)
  }
  if (!res.ok || !body.ok) throw new Error(body?.error || `rimlist: HTTP ${res.status}`)
  return body.result
}

和 Python 的 requests.post(...).json() 完全一样，只是多了错误处理。注意 if (!res.ok || !body.ok) —— 两层都要检查：HTTP 状态码 + 业务层的 ok 标志。

这是"插件挂到宿主界面"的样板。三个概念：

ctx.inject(['服务名'], cb)等宿主提供了这个服务再执行回调。因为插件的加载顺序不保证（和 index.js 里重试注册路由是一个问题）。

owner.effect(fn, label)

这是 DSH 的生命周期管理。fn 里注册的东西会在插件卸载时自动清理。你不用手动反注册 —— 这和 useEffect 返回清理函数是一个思路。

src/client/i18n.js:622-638
let service = null
let bound = null
export function setupLocale(ctx) {
  const l = ctx.get('locale')
  if (!l) return
  service = l
  try {
    l.register(NS, 'zh', zh)
    l.register(NS, 'en', en)
  } catch {}
  bound = l.bind(NS)
}
export function t(key) {
  return bound ? bound(key) : zh[key] ?? key
}

两个设计点：

降级到中文bound ? bound(key) : zh[key] ?? key —— 如果 DSH 没提供 locale 服务（比如独立运行时），直接用 zh 表。再找不到就返回 key 本身。 永远不会显示 undefined。
用模块级变量let service 和 let bound 是全模块共享的单例。这是 React 里少见的"在组件外存状态"，但对"语言"这种全局设置是合理的。

这一行没有任何赋值 —— 它的唯一作用是"订阅一个外部数据源，变了就重画"。subscribe / snapshot 来自 i18n.js。这是 React 18 提供的官方途径，用来把"React 之外的状态"接进来。

CSS 怎么加载的

  if (styleInjected || typeof document === 'undefined') return

为什么是 import css from './styles.css'

正常 JS 不能 import CSS。但 build.mjs 里有个插件（第 2 页看过），把 CSS 文件当纯文本读进来，所以 css 变量就是一个字符串。

然后 create 一个 <style> 标签塞进 <head>。styleInjected 保证只做一次（重复插入会导致样式重复，虽然无害但浪费）。

data-dsh-rimlist 属性是为了方便调试时在 DevTools 里找到这个 style 标签。

chat.js：一个有意思的 hack

src/client/chat.js:8-34
export async function sendToChat(text) {
  const editor = findComposer()
  if (editor) {
    try {
      editor.focus()
      const sel = window.getSelection()
      if (sel) {
        const range = document.createRange()
        range.selectNodeContents(editor)
        range.collapse(false)
        sel.removeAllRanges()
        sel.addRange(range)
      }
      const dt = new DataTransfer()
      dt.setData('text/plain', text)
      const ev = new ClipboardEvent('paste', { clipboardData: dt, bubbles: true, cancelable: true })
      editor.dispatchEvent(ev)
      if (editor.textContent && editor.textContent.includes(text.slice(0, 40))) return 'inserted'
      // some editors ignore synthetic paste: try insertText
      if (document.execCommand && document.execCommand('insertText', false, text)) return 'inserted'
    } catch {}
  }
  try {
    await navigator.clipboard.writeText(text)
  } catch {}
  return 'copied'
}

目标：把"游戏日志摘要"直接填进对话输入框，让用户不用手动复制粘贴。

做法：伪造一个"粘贴"事件

DSH 的输入框是个富文本编辑器（Lexical），直接改 innerHTML 会让它的内部状态错乱。所以：

  1. 找输入框
  2. 把光标移到末尾
  3. 造一个假的 paste 事件，里面装着要插入的文本
  4. 派发它 —— 编辑器以为是用户粘贴的，走正常流程
  5. 验证：检查 textContent 里有没有那段文字（确认真的插进去了）
  6. 备选方案：execCommand('insertText')
  7. 最后的备选：复制到剪贴板，然后告诉用户"你自己粘贴一下"

三层降级，每层失败都往下一层。这是对付"别人的界面不可控"的经典策略。

修改界面时的检查清单

  1. 需要新数据吗？
    如果要后端还不提供的数据，先加 service 方法（第 6 页），再在 store.js 的 actions 里加一个调用。
  2. 改的是"服务器状态"还是"本地草稿"？
    排序、拖拽这类应该只在草稿里改，等用户点保存才写盘。直接调 setActive 会让每次拖动都写一次 ModsConfig.xml。
  3. 用 actions 还是直接 api()？
    用 actions.something()（走 run 包装，有 busy 和错误提示）优先。只有非常特殊的场景才直接 api()。
  4. 新文案加进 i18n 了吗？
    不要在 JSX 里写死中文。加 zh.xxx 和 en.xxx，然后 t('xxx')。
  5. 重新 build + 刷新了吗？
    node build.mjs，然后浏览器硬刷新（Ctrl+Shift+R）。
这一页的收获

React 的核心就三样：组件（函数返回 JSX）、状态（useState + 不可变更新）、副作用（useEffect + 清理）。剩下的都是这三样的组合。

这个项目的前端可能不够"现代"（没有 Context、没有状态库、prop 传得有点多），但它的数据流极其清晰：所有状态在 useRimlist()，所有后端调用在 api()，所有界面在几个 .jsx 里。这种"无聊但清晰"的写法，长期维护起来反而舒服。
