我在这份导读里放了一个可以直接跑的小脚本，它不读你的真实 RimWorld 安装，只用硬编码的假数据，所以绝对安全。

对照第 4 页的理论，逐条验证

观察对应哪条规则
Harmony 排第一（不是 Core）loadBefore: ['ludeon.rimworld'] → 被提拔进 tier 0，且在 Core 前
Core 第二tierOf 返回 0（Core 本体）
Some QoL Tweaks 排第三（明明没有任何规则约束它）tie-break 按名字。tier 2 里它和 VEF / Ratkin 并列，但它必须先满足 VEF 的依赖，所以等 Harmony 就绪后就和 VEF 一起进 ready，名字 "Some QoL Tweaks" < "Vanilla Expanded Framework" → 排前面
VEF 在 Ratkin Race 前modDependencies → 边 vef → ratkin.race
Ratkin Gene Patch 在 Ratkin Race 后loadAfter: ['ratkin.race'] → 边 ratkin.race → patch
RocketMan 最后社区规则 loadBottom → tier 3，永远在最后
诊断 3 warnings → 0三条都是"顺序错了"，排完自然消失
再排一次移动 0 个幂等性 —— 排序算法必须有的性质
现在改一下这个脚本，观察变化

试这几个实验，每个都会让你更懂第 4 页：

  1. 把 rocketman 的社区规则改成 loadTop → 它应该跑到 Harmony 附近（tier 1，但被依赖关系推着走）
  2. 给 some.qol 加 loadAfter: ['ratkin.gene.patch'] → 它应该排到最后
  3. 让 ratkin.race 加 loadBefore: ['vanilla.expanded.core']（与它的依赖矛盾）→ 观察 r.broken 里的破环报告
  4. 把 sortLoadOrder(current, catalog, rules) 改成 sortLoadOrder(current, catalog, rules, { tieBreak: 'current' }) → 看"Some QoL Tweaks"的位置变化

实验二：验证你对 pid 的理解

自己造一个小脚本，测试第 3 页讲的大小写规则：

import { buildModsConfig, parseModsConfig, pid } from '../src/host/xml.js'

console.log(pid('  Ludeon.RimWorld '))   // 'ludeon.rimworld'

const xml = buildModsConfig({
  version: '1.6.4871',
  activeMods: ['Ludeon.RimWorld', 'brrainz.Harmony', 'ludeon.rimworld'],
  knownExpansions: ['Ludeon.RimWorld.Royalty'],
})
console.log(xml)

你会看到写入的 id 全小写且去重（Ludeon.RimWorld 和 ludeon.rimworld 只留一个）。这正是 test/xml.test.js 最后一个测试在断言的事：

test/xml.test.js:44-48
test('buildModsConfig writes lowercase, de-duplicated ids (RimWorld is case-sensitive here)', () => {
  const xml = buildModsConfig({ version: 'v', activeMods: ['Ludeon.RimWorld', 'brrainz.Harmony', 'ludeon.rimworld'], knownExpansions: ['Ludeon.RimWorld.Royalty'] })
  assert.ok(!/[A-Z]/.test(xml.replace(/<\/?[A-Za-z]+>|<\?xml[^>]*>/g, '')))
  assert.deepEqual(parseModsConfig(xml).activeMods, ['ludeon.rimworld', 'brrainz.harmony'])
})

那个正则 /[A-Z]/ 配合 .replace() 先把所有 XML 标签删掉（标签名当然有大小写），剩下的纯内容里不能出现任何大写字母。这是个很聪明的断言写法。

练习一（简单）：加一条测试

目标：证明你理解了诊断。在 test/sorter.test.js 末尾加一个测试，验证"缺依赖"能被报告出来。

参考解法（先自己写，再点开） 
test('diagnose reports a missing dependency as an error', () => {
  const cat = catalogOf(
    mod('ludeon.rimworld'),
    mod('needs.harmony', { modDependencies: [{ packageId: 'brrainz.harmony', displayName: 'Harmony' }] }),
  )
  // Harmony 不在 catalog 里，也没启用 → 应该是 dependency-missing
  const d = diagnose(['ludeon.rimworld', 'needs.harmony'], cat, fakeRules(), { gameMajor: '1.6' })
  const issue = d.issues.find((i) => i.code === 'dependency-missing')
  assert.ok(issue, 'should report a missing dependency')
  assert.equal(issue.level, 'error')
  assert.equal(issue.mod, 'needs.harmony')
  assert.equal(issue.target, 'brrainz.harmony')
  assert.equal(issue.fix, 'subscribe')   // 没装 → 提示去订阅
})

再写一个变体：把 Harmony 加进 catalog 但不启用 → code 应该是 dependency-inactive，fix 是 'activate'。这是第 4 页那个三元表达式的验证。

练习二（中等）：修掉那个效率问题

第 6 页指出 classifyOne 有个重复工作的问题：inspectModFolder 被调了两次，dependents 算了三遍。

src/host/service.js:245-258（现状）
const version = versionOf(m)
const saved = !force ? await modTags.getAuto(key, version) : null
const result = saved?.result || classifyMod(m, await inspectModFolder(m.path, state.game?.major), {
  dependents: state.mods.reduce((n, x) => n + (x.modDependencies || []).filter((d) => pid(d.packageId) === key).length, 0),
})
if (!saved) {
  const f = await inspectModFolder(m.path, state.game?.major)
  const automatic = classifyMod(m, f, { dependents: ...同一串 reduce 又写一遍... })
  await modTags.setAuto(key, version, automatic, signalsSummary(f))
  m.tags = automatic
} else m.tags = saved.result
参考改法

核心思路：把"代价高的计算"提到外面，只做一次。

const version = versionOf(m)
const saved = !force ? await modTags.getAuto(key, version) : null
if (saved) {
  m.tags = saved.result
} else {
  // 只读一次文件夹，只算一次被依赖数
  const facts = await inspectModFolder(m.path, state.game?.major)
  const dependents = state.mods.reduce(
    (n, x) => n + (x.modDependencies || []).filter((d) => pid(d.packageId) === key).length,
    0,
  )
  const automatic = classifyMod(m, facts, { dependents })
  await modTags.setAuto(key, version, automatic, signalsSummary(facts))
  m.tags = automatic
}
const override = await modTags.getAi(key)
if (override) m.tags = override
return m.tags

改动点：

  • 提前分支：saved 有就直接用，不再碰磁盘
  • inspectModFolder 只调一次（原来两次）
  • dependents 只算一次（原来三次）
  • 删掉了那个算完就丢的 result 变量

大文件、几百个 mod 时，这会省掉一半的磁盘 IO —— inspectModFolder 要遍历整个 mod 文件夹数 Defs、patch、DLL、贴图。

改完之后怎么验证

分类是有测试的：node test/classify.test.js。但那测的是 classifyMod（纯函数），不是 classifyOne（有 IO）。

所以更实际的验证是：启动插件，在界面上打开某个 mod 的详情，确认标签还在、内容没变。改"有副作用"的代码时，纯函数测试保不了你，得实际跑一遍。

练习三（稍难）：加一个新的诊断项

假设你想加一条检查："这个 mod 装了但是没启用，而且它有 5 个以上其他 mod 依赖它" —— 这通常意味着你漏开了一个重要的前置库。

这需要动三个地方，正好把整个项目走一遍：

  1. src/host/sorter.js 的 diagnose
    加一段检查。需要知道"有多少已启用的 mod 依赖它" —— 但 diagnose 只收到 activeKeys，而未启用的 mod 不在里面。
  2. src/host/service.js 的 diagnose method
    把 state.mods（全部 mod，不只是启用的）也传进去。这是关键的设计决策 —— 见下面的讨论。
  3. src/host/i18n 不需要改，但界面上如果要显示这个新 code，得在 panels.jsx 里加映射。
这里有个真实的设计问题

diagnose(activeKeys, catalog, ruleStore, opts) 的签名决定了它只能看到已启用的 mod（因为 activeKeys 就是启用列表）。要做"未启用但有依赖"的检查，你得：

  • 方案 A：给 opts 加一个 allMods 字段。改动最小，但让 diagnose 的职责变宽了。
  • 方案 B：在 service 层单独算这个检查，追加到 issues 里。职责清晰，但诊断逻辑散在两处。

项目现有的选择是 A 风格的（duplicates 就是通过 opts 传进去的）。照现有风格做通常是对的 —— 保持一致性比"我认为更好"重要。

这个项目的代码风格总结

如果你要往这里加功能，跟着现有风格写就不会突兀。观察到的规律：

函数式 + 不可变

不用 class。数据更新一律 {...old, key: val}。数组操作用 map/filter 而不是 for + push（虽然也有）。

小函数 + 描述性名字

existedBefore / needsUpdate / wrapResult。名字长但一看就懂，比 x / tmp 好得多。

绝不返回 undefined

parseAbout 每个字段都有默认值；run() 永远返回 { ok, ... }。下游不用判空。

错误不抛，变成数据

工具层用 { ok: false, error }。前端用 toast。只有真正"没法继续"时才 throw（比如参数缺失）。

注释解释"为什么"

看 writeConfig 里那段关于大小写的注释 —— 记录了踩过的坑。这种注释比"这行做什么"有价值一百倍。

兜底优先于报错

破环、删最弱边、RimSort 退回默认算法、catch {} 静默忽略。宁可降级也不要崩。

三个仍然需要小心的地方

地方风险
pid() 无处不在改它影响全库。而且很多地方靠它当 Map key，漏一处就是静默失效（规则不生效但看不出来）。
state 是全局可变的任何函数都能改 state.config。并发安全只靠 serialize()，新写的写操作记得包进去。
slimSteam / indexSteam 必须配对单字母键名。加字段时两边都要改，漏一边就是查不到的字段。

再往后
