四种来源模式

src/host/rules.js:1-20（文件头注释）+ 127-140（obtain 函数）
const obtain = async (key, major) => {
  const def = DB_DEFS[key]
  const c = cfg(key)
  const inZip = typeof def.inZip === 'function' ? def.inZip(major) : def.inZip
  if (c.mode === 'local') {
    if (!c.path) throw new Error(def.label + ': local file path not set')
    return unwrap(await readFile(c.path), inZip, c.path)
  }
  if (c.mode === 'url') {
    if (!c.url) throw new Error(def.label + ': URL not set')
    return fetchText(c.url, inZip)
  }
  return fetchText(def.raw(major), inZip)
}
mode行为什么场景
'github'（默认）从官方 GitHub 拉 raw 文件绝大多数人
'url'任意 URL，支持 raw / .gz / 仓库 .zip用镜像或自己的 fork
'local'直接读磁盘文件已经有 RimSort 的人—— 复用它的 dbs/ 目录，不重复下载
'none'不使用想要纯粹只看 About.xml 的排序
注意 inZip 可能是函数

typeof def.inZip === 'function' ? def.inZip(major) : def.inZip —— 大多数库的压缩包内路径是固定的字符串，但 NoVersionWarning 的路径依赖游戏版本（1.6/ModIdsToFix.xml）。所以定义里写成函数，用时统一判断。

"值可以是值也可以是函数"这个模式在 JS 里很常见（React 的 setState 也是这样），因为区分起来只要一个 typeof。

三层的"取值 → 解压 → 缓存"管道

src/host/rules.js:110-125
const fetchText = async (url, inZip) => {
  const res = await fetchImpl(url, { headers: { 'user-agent': 'dsh-rimlist' } })
  if (!res.ok) throw new Error('HTTP ' + res.status + ' for ' + url)
  const buf = Buffer.from(await res.arrayBuffer())
  return unwrap(buf, inZip, url)
}
const stripBom = (text) => (text.charCodeAt(0) === 0xfeff ? text.slice(1) : text)
const unwrap = (buf, inZip, label) => {
  if (isZip(buf)) {
    const inner = zipFind(buf, inZip)
    if (!inner) throw new Error(`${inZip} not found inside ${label}`)
    return stripBom(isGzip(inner) ? gunzipText(inner) : inner.toString('utf8'))
  }
  if (isGzip(buf)) return stripBom(gunzipText(buf))
  return stripBom(buf.toString('utf8'))
}

不管来源是什么（网络 / 本地、zip / gz / 明文），最后都归到一个字符串。这叫"管道末尾统一"：

GitHub raw ─┐ .zip 压缩包 ─┼→ unwrap() → 纯文本字符串 → JSON.parse() 或正则解析 .gz 压缩 ─┤ 本地文件 ─┘ stripBom() 处理一个 Windows 特有坑： UTF-8 BOM（文件开头三个隐形字节 EF BB BF）会让 JSON.parse() 直接崩。
为什么公司内部代码常在这里出 bug

因为 Windows 记事本保存 UTF-8 时会加 BOM。这个 3 行的小函数救了无数人。看到 0xfeff 这个魔数，就是在检查 BOM。

缓存策略：先读旧的，后台更新

src/host/rules.js:302-316
const ensure = async ({ major, maxAgeHours = 24 * 7, force = false } = {}) => {
  await mkdir(dbDir, { recursive: true })
  await Promise.all([...DB_KEYS.map((k) => loadCached(k, major)), loadUser()])
  const jobs = []
  for (const key of DB_KEYS) {
    if (cfg(key).mode === 'none') continue
    if (key === 'noVersionWarning' && !major) continue
    // Local files are always re-read (cheap) so edits show up; remote by age.
    const need = cfg(key).mode === 'local' || force || (await ageHours(cachePath(key, major))) > maxAgeHours
    if (need) jobs.push(refresh(key, major).catch((e) => (state[key].error = String(e.message || e))))
  }
  await Promise.all(jobs)
  return status()
}

这个函数只用了 15 行，但把"离线优先"这件事做对了：

  1. 先全部读本地缓存
    不管新旧，先加载。这意味着断网也能用 —— 有缓存就行。
  2. 再判断哪些需要更新
    本地文件永远重读（反正是读磁盘，很快，而且用户可能刚改过）。网络文件看年龄，超过 maxAgeHours（默认 7 天 = 24*7）才更新。
  3. 并发更新，失败不影响整体
    .catch((e) => (state[key].error = ...)) —— 某个库下载失败，只记在它的 error 字段里，其他库照常。界面会在设置里显示"这个库有错误"，但功能继续可用。
.catch() 返回的是赋值表达式的值

.catch((e) => (state[key].error = String(...))) 里箭头函数直接返回赋值结果。虽然这里不在乎返回值，但这保证了 Promise.all 不会因为一个失败就整体 reject。这是"并发 + 容错"的标准写法。

Python 里你会需要 asyncio.gather(..., return_exceptions=True) 或者给每个任务包 try。JS 这里更简洁。

规则的数据形状

规则库的原始 JSON 格式五花八门（数组 / 对象 / 布尔 / 带 value 的对象），所以有一个规范化函数把它们统一：

src/host/rules.js:143-160
const normalizeRules = (raw) => {
  const out = {}
  if (!raw || typeof raw !== 'object') return out
  for (const [k, v] of Object.entries(raw)) {
    if (!v || typeof v !== 'object') continue
    const r = { ...EMPTY_RULES, loadAfter: {}, loadBefore: {}, incompatibleWith: {}, ignoreIncompatible: {} }
    for (const field of ['loadAfter', 'loadBefore', 'incompatibleWith', 'ignoreIncompatible']) {
      const src = v[field]
      if (!src) continue
      if (Array.isArray(src)) for (const t of src) r[field][pid(t)] = { name: [] }
      else if (typeof src === 'object') for (const [t, info] of Object.entries(src)) r[field][pid(t)] = { name: Array.isArray(info?.name) ? info.name : info?.name ? [String(info.name)] : [], comment: info?.comment || undefined }
    }
    if (v.loadTop && (v.loadTop === true || v.loadTop.value)) r.loadTop = { comment: v.loadTop.comment || '' }
    if (v.loadBottom && (v.loadBottom === true || v.loadBottom.value)) r.loadBottom = { comment: v.loadBottom.comment || '' }
    out[pid(k)] = r
  }
  return out
}

输出的形状永远是：

{
  'some.mod': {
    loadAfter:        { 'other.mod': { name: ['Other Mod'], comment: undefined } },
    loadBefore:       {},
    incompatibleWith: {},
    ignoreIncompatible: {},
    loadTop:    null,                      // 或 { comment: '' }
    loadBottom: { comment: '' },
  },
}

为什么统一成这个形状：因为排序算法（第 4 页）读规则时只需要 Object.entries(rules.loadAfter)，不在乎它原来是什么格式。所有格式差异都被隔离在这个函数里了。

注意 pid(t) 在这里的角色

规则库里的 packageId 大小写可能和你的 About.xml 不一样。这里统一转小写后当 key，和 catalog 的 key 命名一致，才能对上。如果哪一步漏了 pid()，规则就会静默失效 —— 排序看起来"没问题"，但规则没生效。这类 bug 最难查。

合并多个来源：rulesFor

src/host/rules.js:424-436
const rulesFor = (packageId) => {
  const k = pid(packageId)
  const merged = { loadAfter: {}, loadBefore: {}, incompatibleWith: {}, ignoreIncompatible: {}, loadTop: null, loadBottom: null }
  const apply = (r, source) => {
    if (!r) return
    for (const f of ['loadAfter', 'loadBefore', 'incompatibleWith', 'ignoreIncompatible']) for (const [t, info] of Object.entries(r[f] || {})) merged[f][t] = { ...info, source }
    if (r.loadTop) merged.loadTop = { ...r.loadTop, source }
    if (r.loadBottom) merged.loadBottom = { ...r.loadBottom, source }
  }
  if (cfg('community').mode !== 'none') apply(state.community.rules[k], 'community')
  if (state.userEnabled) apply(state.user.rules[k], 'user')
  return merged
}
顺序就是优先级 —— 这里只有两行，但很关键

先 apply community，后 apply user。同一个目标 mod，后写的覆盖前面的，所以用户规则永远赢。

同时每条规则被贴上 source 标签（'community' 或 'user'），后面排序时用它查优先级表 PRIORITY，界面也用它显示"这条规则来自哪"。

自定义规则：增删改

这是"社区库错了怎么办"的答案。看添加规则的核心逻辑，它有几处小巧思：

src/host/rules.js:363-382
const addUserRule = async ({ packageId, kind, target, comment, name }) => {
  const k = pid(packageId)
  if (!k) throw new Error('packageId required')
  const r = state.user.rules[k] || (state.user.rules[k] = { loadAfter: {}, loadBefore: {}, incompatibleWith: {}, ignoreIncompatible: {}, loadTop: null, loadBottom: null })
  if (!r.ignoreIncompatible) r.ignoreIncompatible = {}
  if (kind === 'loadTop' || kind === 'loadBottom') {
    r[kind] = { comment: comment || '' }
    if (kind === 'loadTop') r.loadBottom = null
    else r.loadTop = null
  } else if (kind === 'loadAfter' || kind === 'loadBefore' || kind === 'incompatibleWith' || kind === 'ignoreIncompatible') {
    const t = pid(target)
    if (!t) throw new Error('target packageId required')
    if (t === k) throw new Error('a mod cannot reference itself')
    r[kind][t] = { name: name ? [name] : [], comment: comment || undefined }
    const opposite = kind === 'loadAfter' ? 'loadBefore' : kind === 'loadBefore' ? 'loadAfter' : kind === 'incompatibleWith' ? 'ignoreIncompatible' : kind === 'ignoreIncompatible' ? 'incompatibleWith' : null
    if (opposite) delete r[opposite][t]
  } else throw new Error('unknown rule kind: ' + kind)
  await saveUser()
  return r
}
互斥自动清理 加 loadAfter: X 就自动删掉 loadBefore: X。加 incompatibleWith 就删 ignoreIncompatible。
不用让用户自己先删旧的 —— 否则很容易出现"我加了规则但没生效"的困惑。
loadTop / loadBottom 互斥 if (kind === 'loadTop') r.loadBottom = null —— 一个 mod 不可能既置顶又置底。
t === k 检查 禁止自引用。第 4 页 addEdge 里也有同样的检查，两处都防 —— 因为这里的数据可能被手工改 JSON 塞进来。
每次改都 saveUser() 立刻写盘。规则是用户手工配置的，丢了很气人。宁可多写几次磁盘。

写盘为什么要"先写 .tmp 再 rename"

src/host/rules.js:93-98
const writeJsonAtomic = async (file, value) => {
  await mkdir(path.dirname(file), { recursive: true })
  const tmp = file + '.tmp'
  await writeFile(tmp, JSON.stringify(value), 'utf8')
  await rename(tmp, file)
}
这个模式叫 原子写入，全项目都在用

如果直接 writeFile(目标文件)，写到一半程序被杀掉，文件就坏了（只有半个 JSON）。

先写临时文件，写完再 rename。而 rename 在同一个磁盘分区内是原子操作 —— 要么成功（新文件完整生效），要么失败（旧文件完好）。永远不会出现半截文件。

Python 里你会用 os.replace()，道理一样。这是配置类文件必须遵守的规矩。

网络抓取的一处细节

从 URL 导入列表时，要处理各种粘贴板服务的 URL 变形：

src/host/service.js:515-527
const importUrl = async ({ url, name, save = true }) => {
  const f = fetchImpl || globalThis.fetch
  let u = String(url || '').trim()
  // Normalise common hosts to raw text.
  u = u.replace(/^https:\/\/github\.com\/([^/]+\/[^/]+)\/blob\//, 'https://raw.githubusercontent.com/$1/')
  if (/^https:\/\/rentry\.(co|org)\/[\w-]+$/.test(u)) u += '/raw'
  if (/^https:\/\/gist\.github\.com\//.test(u) && !/\/raw/.test(u)) u += '/raw'
  if (/pastebin\.com\/(?!raw)/.test(u)) u = u.replace('pastebin.com/', 'pastebin.com/raw/')
  const res = await f(u, { headers: { 'user-agent': 'dsh-rimlist' } })
  if (!res.ok) throw new Error('HTTP ' + res.status + ' fetching ' + u)
  const text = await res.text()
  return importText({ text, name, save, url: String(url) })
}

玩家粘的是浏览页面的 URL，但程序需要原始文本。四个规则各自转换：

Rentryrentry.co/abcrentry.co/abc/raw
Gistgist.github.com/...末尾加 /raw
Pastebinpastebin.com/XYZpastebin.com/raw/XYZ
(?!raw) 是"否定先行断言"

/pastebin\.com\/(?!raw)/ 意思是"pastebin.com/ 后面不是 raw"。所以已经带 /raw 的 URL 不会被重复加。/(?!...)/ 这个语法 Python 的 re 也支持，写法一模一样。

为什么 steamDB 要"瘦身"

src/host/rules.js:161-179
const slimSteam = (raw) => {

原始 steamDB 有几十 MB（每个工坊 mod 的完整信息）。这里只留 8 个字段，键名缩成一个字母（p = packageId，n = name，d = dependencies…）。

这是有代价的

单字母键名省了内存和磁盘，但可读性差了。如果以后要加字段，必须同时改 slimSteam 和 indexSteam（下面那个展开回全名的函数），漏一个就是诡异的 undefined。

  const byPfid = new Map()
  for (const [pfid, e] of Object.entries(slim.database || {})) {
    const entry = { pfid, packageId: e.p, name: e.n, authors: e.a, url: e.u, gameVersions: e.v || [], dependencies: e.d || {}, unpublished: !!e.x, isApp: !!e.app }
    byPfid.set(pfid, entry)
    if (e.p && !byPid.has(e.p)) byPid.set(e.p, entry)
  }
  state.steam.byPid = byPid
  state.steam.byPfid = byPfid
  state.steam.version = slim.version
}

注意建了两个索引：按 packageId 查（诊断时用），按工坊 ID 查（诊断里的链接用）。同一个 entry 对象被两个 Map 引用 —— 省内存，改一处两边都看到。

这一页的设计经验

① 配置形状统一

DB_DEFS 里五个库用同一套键名，所以一个 ensure() 处理全部。加新库只要加一条定义。

② 规范化隔离

normalizeRules 把五六种原始格式变成一个形状。所有脏活在这一个函数里，下游都是干净数据。

③ 离线优先

先读缓存（一定成功），再后台更新（可能失败）。失败只记 error 字段，不影响功能。

④ 原子写入

所有配置写入都走 .tmp + rename。断电也不会产生坏文件。

⑤ 优先级靠调用顺序

rulesFor 里先 community 后 user，后者覆盖前者。没有复杂的优先级数值运算，就靠顺序。

⑥ 互斥自动维护

加 loadAfter 自动删 loadBefore。用户不用懂内部结构，不会产生矛盾状态。
