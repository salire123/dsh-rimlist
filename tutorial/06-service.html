最重要的 20 行：串行化队列

这个文件里最精妙的地方，只有 5 行：

src/host/service.js:72-77
let queue = Promise.resolve()
const serialize = (fn) => {
  const p = queue.then(fn, fn)
  queue = p.catch(() => {})
  return p
}
它在解决什么问题

假设用户在界面上疯狂点"保存"，同时 AI 也触发了"排序并保存"。两次操作同时读写 state.config 和 ModsConfig.xml。结果可能是写了一半 A 的结果、一半 B 的结果。

这三个类别的所有写操作都必须排队 —— 一次只跑一个。

逐行拆解

let queue = Promise.resolve() 起点是一个"已经完成"的 Promise。可以把它想成一个空的队列头。注意是 let 不是 const —— 它会被重新赋值。
queue.then(fn, fn) 成功和失败都调 fn。意思是"不管上一个操作成功还是失败，都接着跑我这一个"。（如果只写 queue.then(fn)，上一个失败了，后面全部会跳过。）
queue = p.catch(() => {}) 队列尾更新成"这个操作的 Promise，但吞掉错误"。为什么吞？因为队列尾如果是个 rejected Promise，后面所有人都会收到 unhandled rejection 警告。真正的错误已经通过 return p 交给调用者了，队列本身只需要知道"做完了"。
return p 返回原始的 Promise（带着可能的错误），调用者能正常 await 和捕获。

用法：

src/host/service.js:321-336（setActive 是串行化的）
const setActive = async (ids, { save = true } = {}) =>
  serialize(async () => {
    await init()
    const seen = new Set()
    const next = []
    for (const id of ids) {
      const k = pid(id)
      if (!k || seen.has(k)) continue
      seen.add(k)
      const m = state.catalog.get(k)
      next.push(m ? m.packageId : id)
    }
    state.config = { ...state.config, activeMods: next }
    if (save) await writeConfig()
    return { active: next.map(pid) }
  })
注意 serialize 包的是"整个写操作"

不是包 writeConfig 一行，而是包"校验 id → 去重 → 更新 state → 写文件"这一整段。因为这几步必须原子完成 —— 中间插进另一个操作就乱了。

这是"临界区"的概念，和 Python 里 with lock: 包住一段代码完全一样。

init()：只跑一次的初始化

src/host/service.js:150-157
const init = () =>
  (state.ready ||= (async () => {
    await mkdir(dataDir, { recursive: true })
    await loadSettings()
    await rescan()
    // Rules load from cache immediately; network refresh in background.
    rules.ensure({ major: state.game?.major, maxAgeHours: state.settings.dbMaxAgeHours }).catch((e) => log('rules ensure failed: ' + e.message))
  })())

这五行是整个文件的启动钥匙。几乎每个 method 的第一行都是 await init()。

||= "如果左边是假值（null），就执行右边并赋值"。所以第一次调用时创建 Promise 存进 state.ready，之后所有调用都直接返回同一个 Promise。保证初始化只跑一次。
为什么这是并发安全的 因为 JS 单线程。第一个调用者执行 state.ready ||= ... 时不会被别人打断。第二个调用进来时 state.ready 已经有值了。
最后一行不 await rules.ensure(...).catch(...) 没有 await。规则库下载可能要好几十秒，不能让初始化卡在那。先用缓存跑起来，下载完了自然生效。
Python 等价物

    if _ready is None:

视图层：modView

内部 mod 对象字段很多（30+ 个），而且有一堆不该给前端看的（比如 path 里的完整磁盘路径其实要给，但 mtime 就不用）。所以有一个"视图函数"把关：

src/host/service.js:270-296
const modView = (m) => ({
  key: m.key,
  packageId: m.packageId,
  name: m.name,
  author: m.author,
  kind: m.kind,
  source: m.source,
  path: m.path,
  publishedFileId: m.publishedFileId,
  steamAppId: m.steamAppId,
  url: m.url,
  supportedVersions: m.supportedVersions,
  modVersion: m.modVersion,
  hasPreview: !!m.preview,
  invalid: m.invalid,
  dependsOn: m.modDependencies.map((d) => ({ packageId: pid(d.packageId), name: d.displayName, url: d.steamWorkshopUrl || d.downloadUrl })),
  loadAfter: m.loadAfter.map(pid),
  loadBefore: m.loadBefore.map(pid),
  forceLoadAfter: m.forceLoadAfter.map(pid),
  forceLoadBefore: m.forceLoadBefore.map(pid),
  incompatibleWith: m.incompatibleWith.map(pid),
  nvw: rules.nvwCovers(m.key),
  rules: rules.rulesFor(m.key),
  replacement: rules.replacementFor({ publishedFileId: m.publishedFileId, packageId: m.key }) || null,

注意几个转换：

hasPreview: !!m.preview内部存的是文件路径，前端只需要"有没有"。!! 转成布尔值，也避免了把服务器路径暴露给浏览器。
.map(pid)所有规则里的 packageId 全部转小写，和 catalog 的 key 一致。前端拿到的就是能直接比较的形式。
dependsOn把内部的 modDependencies（对象数组）改名并简化成前端要的三字段。
实时计算字段nvw、rules、replacement、update 都不是存在 mod 上的，而是调用时现算。所以规则库更新后不用重新扫描就能看到新规则。
这个"视图层"模式的三个好处
  1. 接口稳定：内部结构随便改，前端不受影响（改了视图函数就行）
  2. 省流量：不把 mtime、folder、loadFolderVersions 这些没用的发给浏览器
  3. 安全性：不想暴露的字段不出现在视图里

const dispatch = async (method, args = {}) => {
  const fn = methods[method]
  if (!fn) throw new Error('unknown method: ' + method)
  return fn(args || {})
}

return { init, dispatch, state, rules, lists, activeKeys, effectivePaths }

八行。dispatch 就是按名字查表调用。没有 switch、没有 if 链。加一个新方法 = 在 methods 里加一行。

为什么 args || {}

因为前端可能传 null（JSON 里 undefined 会被丢掉）。如果某个 method 的定义是 async ({ ids }) => ...，而 args 是 null，解构会崩：Cannot destructure property 'ids' of null。这一层兜底让所有 method 都能安全地解构参数。

① 只算不存的 sortIds

src/host/service.js:592-599
sortIds: async ({ ids, tieBreak }) => {
  await init()

和 sort（带 save=true 会写盘）几乎一样，但不写盘。前端拿 order 存进"草稿"。

before / after 这个设计很贴心

如果不改好，用户就不会点保存，草稿一丢就回到原样。这是个很好的交互决策。

② 挂载点：writeConfig

全项目只有这一处写 ModsConfig.xml：

src/host/service.js:339-361
const BACKUP_DIR = 'backups'
const writeConfig = async () => {
  const f = modsConfigPath()
  if (!f) throw new Error('RimWorld config directory not found; set configDir in settings')
  const cfg = state.config
  const exp = new Set(cfg.knownExpansions.map(pid))
  for (const k of cfg.activeMods.map(pid)) if (/^ludeon\.rimworld\./.test(k)) exp.add(k)
  const seen = new Set()
  const ids = cfg.activeMods.map(pid).filter((k) => k && !seen.has(k) && seen.add(k))
  const xml = buildModsConfig({ version: cfg.version || state.game?.full || '', activeMods: ids, knownExpansions: [...exp] })
  // Backup first.
  const bdir = path.join(dataDir, BACKUP_DIR)
  await mkdir(bdir, { recursive: true })
  if (await exists(f)) {
    const stamp = new Date().toISOString().replace(/[:.]/g, '-')
    await copyFile(f, path.join(bdir, `ModsConfig.${stamp}.xml`))
    await pruneBackups(bdir)
  }
  await writeFile(f + '.tmp', xml, 'utf8')
  await rename(f + '.tmp', f)
  state.configMtime = (await stat(f)).mtimeMs
}

这个函数有五个值得学的点：

  1. 自动补齐 knownExpansions
    所有 ludeon.rimworld.* 的 mod 自动加进"已知资料片"列表。免得因为忘了写导致游戏提示"你需要 DLC"。
  2. 小写 + 去重
    那个反复出现的 filter((k) => k && !seen.has(k) && seen.add(k)) 模式。
  3. 先备份再写
    用万无一失的顺序：copyFile 备份 → 写 .tmp → rename。
  4. 备份文件名用 ISO 时间戳
    new Date().toISOString().replace(/[:.]/g, '-') —— Windows 文件名不能有冒号，所以把 : 和 . 换成 -。
  5. 写完更新 configMtime
    否则下次 loadConfig() 会以为文件被外部改了，白白重读一遍（而且可能读到刚写的自己的内容，无谓开销）。
备份修剪策略

pruneBackups 只保留最新的 settings.backupKeep 个（默认 20）。因为文件名里有 ISO 时间戳，按文件名排序就等于按时间排序，所以 .sort() 之后砍掉前面（最老的）即可。不需要解析时间。

这是个很实用的技巧：合理设计文件名，省掉后续所有时间解析。

③ 跨模块协作：applyList

看一个同时用到 lists、catalog、config 的复合操作：

src/host/service.js:476-492
const applyList = async (id, { mode = 'replace' } = {}) =>
  serialize(async () => {
    await init()
    const l = await lists.get(id)
    if (!l) throw new Error('list not found: ' + id)
    const ids = l.mods.map((m) => m.packageId)
    const missing = ids.filter((x) => !state.catalog.has(pid(x)))
    let next = ids
    if (mode === 'merge') {
      const cur = state.config.activeMods
      const set = new Set(cur.map(pid))
      next = [...cur, ...ids.filter((x) => !set.has(pid(x)))]
    }
    state.config = { ...state.config, activeMods: next.filter((x) => state.catalog.has(pid(x))) }
    await writeConfig()
    return { active: activeKeys(), missing: missing.map((x) => ({ packageId: x, ...(l.mods.find((m) => m.packageId === x) || {}) })) }
  })
两种模式replace 直接换掉整个列表；merge 把列表里我还没有的追加到当前列表后面。
先算 missing在过滤之前就算出来，这样能告诉用户"这个列表里有 5 个 mod 你没装"。
写盘时过滤未安装的next.filter((x) => state.catalog.has(pid(x))) —— 没装的 mod 不能写进 ModsConfig，否则游戏会报错或忽略。但 missing 里仍然报告它们，让用户知道缺了什么。
返回体带完整信息{ packageId, ...(l.mods.find(...) || {}) } —— 把列表里记录的完整 mod 信息（名字、工坊 ID）也带上，前端能直接显示"缺：某某 Mod"而不是光秃秃的 packageId。

一处值得警惕的代码

不是所有代码都漂亮。看 classifyOne：

src/host/service.js:234-259
const classifyOne = async (packageId, { force = false, ai = null } = {}) => {
  await init()
  const m = state.catalog.get(pid(packageId))
  if (!m) return null
  const key = m.key
  if (ai) {
    const result = finalize({ ...ai, mod_name: m.name, ... })
    await modTags.setAi(key, result)
    m.tags = result
    return result
  }
  const version = versionOf(m)
  const saved = !force ? await modTags.getAuto(key, version) : null
  const result = saved?.result || classifyMod(m, await inspectModFolder(m.path, state.game?.major), {
    dependents: state.mods.reduce((n, x) => n + (x.modDependencies || []).filter((d) => pid(d.packageId) === key).length, 0),
  })
  if (!saved) {
    const f = await inspectModFolder(m.path, state.game?.major)
    const automatic = classifyMod(m, f, { dependents: state.mods.reduce((n, x) => n + (x.modDependencies || []).filter((d) => pid(d.packageId) === key).length, 0) })
    await modTags.setAuto(key, version, automatic, signalsSummary(f))
    m.tags = automatic
  } else m.tags = saved.result
  const override = await modTags.getAi(key)
  if (override) m.tags = override
  return m.tags
}
这里有两个明显的问题
  1. inspectModFolder 被调了两次（第 247 行和第 251 行），classifyMod 也被调了两次，dependents 那串 reduce 写了三遍。磁盘 IO 白白做了一倍 —— 对一个要扫描几百个 mod 的操作来说，这是实打实的浪费。
  2. result 变量算出来了，但在 !saved 分支里又重新算了一遍 automatic，result 就白算了。

这很可能是重构过程中的残留（先写了 saved 分支，后来加缓存时没清理干净）。

这是个很好的练习素材

如果你想知道自己有没有真的读懂，试着把这段重写成：只调一次 inspectModFolder，只算一次 dependents。第 8 页会给出一个参考改法。

service.js ├─ 1-20 import（13 个本地模块，可见它是总汇合点） ├─ 22-46 DEFAULT_SETTINGS（所有默认配置，注释写得很全） ├─ 48-58 createService 开始：建 6 个子 store ├─ 60-71 state 对象 ├─ 72-77 serialize 串行化队列 ★ ├─ 79-121 设置：loadSettings / saveSettings / effectivePaths / modsConfigPath ├─ 123-148 扫描：rescan / loadConfig ├─ 150-157 init（只跑一次） ★ ├─ 159-232 版本追踪 / 自动备份 / updateInfo ├─ 234-267 分类：classifyOne / classifyAll ├─ 269-296 视图：modView ★ ├─ 297-318 snapshot ★ ├─ 320-389 改顺序：setActive / writeConfig / pruneBackups / listBackups / restoreBackup ├─ 391-419 sort / explain ├─ 421-557 列表：originOf / saveList / applyList / importText / importUrl / exportList / compareList ├─ 559-1180 methods 大字典 ★（占一半篇幅） └─ 1182-1188 dispatch + return ★

带 ★ 的是核心，加起来不到 150 行。其余都是具体业务的填充。

读这个文件的正确姿势

  1. 先读 48-157 行（到 init 结束）
    理解 state、serialize、init。这三样是全文件的地基。
  2. 再读 1182-1188（dispatch）
    知道入口长什么样，心里就有数：剩下的 600 行都是"可以被 dispatch 调到的方法"。
  3. 然后按需查 methods
    想知道"排序怎么走的"就查 sortIds；想知道"保存怎么写的"就查 setActive → writeConfig。
  4. 跳过你暂时不关心的部分
    git、日志解析、分类算法 —— 这些是独立功能，不影响理解主干。想用再回来看。
顺便：怎么快速定位一个方法

在 VS Code 里按 Ctrl+Shift+O（大纲）能列出文件里所有符号。service.js 里会有几十个 xxx: async (...) —— 跳转很快。

命令行也行：grep -n "^ [a-zA-Z]*: async" src/host/service.js 就能列出所有 method 的行号。
