① 找路径：一份很实在的"跨平台兼容"代码

RimWorld 在三个平台上的安装位置完全不同，而且 Steam 库可能在任意磁盘上。这段代码就是在解决这件事。

src/host/paths.js:21-56
async function steamLibraryRoots() {
  const roots = new Set()
  const bases = platform() === 'win32'
    ? [
        process.env['ProgramFiles(x86)'] && path.join(process.env['ProgramFiles(x86)'], 'Steam'),
        process.env.ProgramFiles && path.join(process.env.ProgramFiles, 'Steam'),
        'C:\\Program Files (x86)\\Steam',
        'C:\\Program Files\\Steam',
        'D:\\Steam',
        'D:\\SteamLibrary',
      ].filter(Boolean)
    : platform() === 'darwin'
      ? [path.join(H, 'Library/Application Support/Steam')]
      : [ ...几个 Linux 常见位置... ]
  for (const base of bases) if (await exists(path.join(base, 'steamapps'))) roots.add(base)

  // libraryfolders.vdf lists extra library locations.
  for (const base of [...roots]) {
    const vdf = path.join(base, 'steamapps', 'libraryfolders.vdf')
    if (!(await exists(vdf))) continue
    try {
      const text = await readFile(vdf, 'utf8')
      for (const m of text.matchAll(/"path"\s+"([^"]+)"/g)) {
        const p = m[1].replace(/\\\\/g, '\\')
        if (await exists(path.join(p, 'steamapps'))) roots.add(p)
      }
    } catch {}
  }
  return [...roots]
}

要点：

嵌套三元a ? ... : b ? ... : c 就是 Python 的 x if a else y if b else z，但缩进表达力更强，这里用了换行对齐来看。
process.env.X && path.join(...)如果环境变量不存在就是 undefined，后面的 .filter(Boolean) 会把它去掉。这是"可选候选路径"的惯用法。
new Set() 去重同一个 Steam 目录可能从多个途径发现，用 Set 保证不重复。
for (const base of [...roots])注意这个 [...roots]。因为循环体内会往 roots 里 add。先复制一份快照来遍历，避免"遍历中修改集合"。Python 里你会写 for base in list(roots):。
为什么解析 VDF 用正则而不用解析器

Steam 的 libraryfolders.vdf 是一种自定义格式，只有一处需要读（每个库的 path 字段）。为正则能搞定的事加一个依赖不划算。注释也说明了在干什么。这是很务实的取舍。

路径是什么里面有什么
gameDir游戏本体Data/（Core + DLC）、Mods/（本地 mod）、Version.txt
workshopDir创意工坊 mod.../content/294100/<数字ID>/。294100 是 RimWorld 的 Steam AppID
localModsDir手动装的 mod游戏目录下的 Mods/
configDir存档和设置ModsConfig.xml 就在这里！
Version.txt 怎么变成 "1.6"

文件内容长这样：1.6.4871 rev598。所以需要一个提取函数：

export function majorVersion(v) {
  const m = String(v || '').match(/(\d+)\.(\d+)/)
  return m ? m[1] + '.' + m[2] : null
}

（paths.js:117）.match() 返回数组 ['1.6', '1', '6']（第 0 项是整个匹配），或者 null。Python: re.search(r'(\d+)\.(\d+)', v)。

为什么这个很重要：后面判断"这个 mod 支不支持当前版本"全靠这个 "1.6" 字符串。

② 扫描：把文件夹变成对象

src/host/scan.js:111-146
export async function scanMods({ gameDir, localModsDir, workshopDir, major, extraDirs = [] }) {
  const found = []
  const push = async (base, source) => {
    if (!base || !(await exists(base))) return
    const names = await listDirs(base)
    await Promise.all(
      names.map(async (name) => {
        const m = await scanOne(path.join(base, name), source, major, name)
        if (m) found.push(m)
      }),
    )
  }
  if (gameDir) await push(path.join(gameDir, 'Data'), 'official')
  await push(localModsDir, 'local')
  for (const d of extraDirs) await push(d, 'local')
  await push(workshopDir, 'workshop')

  // Resolve duplicates: official > local > workshop (game's own precedence).
  const rank = { official: 0, local: 1, workshop: 2 }
  found.sort((a, b) => rank[a.source] - rank[b.source] || a.name.localeCompare(b.name))
  const byId = new Map()
  const duplicates = new Map()
  for (const m of found) {
    if (!byId.has(m.key)) byId.set(m.key, m)
    else {
      const d = duplicates.get(m.key) || [byId.get(m.key).path]
      d.push(m.path)
      duplicates.set(m.key, d)
    }
  }
  ...
  return { mods, byId, duplicates: [...duplicates.entries()].map(([key, paths]) => ({ key, paths })) }
}

这段代码做了四件事，顺序很重要：

  1. 按来源依次扫描
    Data/（官方）→ Mods/（本地）→ 额外的本地目录 → 工坊。push 是个内部小函数，把"扫一个目录"这件事参数化。这个叫闭包 + 高阶函数：push 捕获了外层的 found 数组。
  2. 并发扫每个子文件夹
    Promise.all(names.map(async ...))：几百个文件夹同时读，比一个个来快好几倍。
  3. 排序决定优先级
    rank[a.source] - rank[b.source]：official(0) 排前面，workshop(2) 排后面。注释说明了原因：这是游戏自己的优先级 —— 如果本地有一个同名 mod 也有工坊版本，游戏用本地的。
  4. 建 Map，顺手记下重复
    if (!byId.has(m.key)) 第一名的赢。后面的记进 duplicates（诊断时报告"这个 mod 装了两份"）。
found.sort(...) 里的 || 又是一个多级排序

先按来源优先级排，来源相同时按名字排（localeCompare 是本地化的字符串比较，中文能正确排）。这是这个项目的招牌写法，第 1 页提过一次。

RimWorld 的文件名大小写不统一（尤其是在 Linux 上），所以代码要挨个试：

async function readAboutIn(dir) {
  // About.xml may be About/About.xml with varying case on case-sensitive FS.
  for (const rel of ['About/About.xml', 'about/about.xml', 'About/about.xml', 'about/About.xml']) {
    const p = path.join(dir, rel)
    if (await exists(p)) return { path: p, xml: await readFile(p, 'utf8') }
  }
  return null
}

async function readPublishedId(dir) {
  for (const rel of ['About/PublishedFileId.txt', 'about/PublishedFileId.txt']) {
    const p = path.join(dir, rel)
    if (await exists(p)) {
      const t = (await readFile(p, 'utf8')).trim()
      if (/^\d+$/.test(t)) return t
    }
  }
  return null
}

Windows 上文件系统不区分大小写，这些循环第一次就命中。Linux 上就真的一一试探 —— 这样代码在两个平台都对。

key vs packageId —— 这个区别要记牢

key = pid(meta.packageId)，永远小写；packageId 保留原样。为什么需要两个？

  • 比较时用 key：RimWorld 自己就区分大小写，所以 Ludeon.RimWorld 和 ludeon.rimworld 是两个不同的东西，写进 ModsConfig 会导致游戏显示灰化的重复项。
  • 显示和写文件时用 packageId：保留作者写的原样。

整份代码里凡是 .get(x)、.has(x)、Set 操作，都用 key。所以在入口处就统一 pid() 一下。

这段代码里有个 in 操作符

key in KNOWN_EXPANSIONS —— 检查对象的键是否存在。Python 是 key in dict，完全一样。注意别和 of 搞混：in 用于对象查键 / 数组查索引，of 用于遍历值。

为什么每个列表都是 { li: [...] } 套一层

解析主函数

src/host/xml.js:49-74
export function parseAbout(xml, major) {
  const doc = parser.parse(xml)
  const m = doc.ModMetaData || doc.modMetaData || {}
  const pick = (base, versionedKey) => {
    const v = byVersion(m[versionedKey], major)
    return v !== null ? v : liList(m[base])
  }
  const packageId = text(m.packageId)
  return {
    packageId,
    name: text(m.name) || packageId,
    author: text(m.author) || liList(m.authors).join(', ') || '',
    url: text(m.url) || null,
    description: text(m.description),
    modVersion: text(m.modVersion) || null,
    supportedVersions: liList(m.supportedVersions).map((v) => v.match(/\d+\.\d+/)?.[0] || v),
    targetVersion: text(m.targetVersion) || null,   // legacy (pre-1.1) field
    loadAfter: pick('loadAfter', 'loadAfterByVersion'),
    loadBefore: pick('loadBefore', 'loadBeforeByVersion'),
    forceLoadAfter: liList(m.forceLoadAfter),
    forceLoadBefore: liList(m.forceLoadBefore),
    incompatibleWith: pick('incompatibleWith', 'incompatibleWithByVersion'),
    modDependencies: depList(m.modDependencies, major, m.modDependenciesByVersion),
    steamAppId: text(m.steamAppId) || null,
  }
}

几个值得注意的设计：

全部字段都给默认值每个字段后面都有 || '' 或 || null 或 liList()（空数组）。绝不返回 undefined。这让下游代码不用到处判空。
|| packageId没有 name 就用 packageId 当名字 —— 总得有个能显示的东西。
pick() 闭包因为"优先用带版本号的字段，否则用普通字段"这件事要重复三次（loadAfter / loadBefore / incompatibleWith），所以抽成一个闭包。捕获了外层的 m 和 major。
.map((v) => v.match(/\d+\.\d+/)?.[0] || v)版本号统一成 "1.6" 格式。有人写 "1.6"，有人写 "1.6.4871"，提取前两段。

带版本号的条件字段（RimWorld 1.4+ 的新玩法）

新版 RimWorld 允许 mod 针对不同游戏版本声明不同的规则：

XML 长这样
<loadAfterByVersion>
  <v1.5><li>old.mod</li></v1.5>
  <v1.6><li>new.mod</li></v1.6>
</loadAfterByVersion>
src/host/xml.js:22-28
function byVersion(node, major) {
  if (!node || typeof node !== 'object' || !major) return null
  const key = 'v' + major
  if (node[key] !== undefined) return liList(node[key])
  return null
}

注意它返回 null 而不是空数组 —— 这是刻意的：pick() 里用 v !== null 来判断"到底有没有这个版本的覆盖块"。如果返回 []，就分不清"声明了但为空"和"根本没声明"了。

这是个通用的设计原则

用 null 表示"没有这个信息"，用 [] / '' 表示"有信息但是空的"。两者语义不同，不能混用。Python 里也常这么区分 None 和 []。

依赖列表的特殊处理

src/host/xml.js:31-43
function depList(node, major, versioned) {
  let items = asArray(node && node.li)
  if (versioned && typeof versioned === 'object' && versioned['v' + major]) items = asArray(versioned['v' + major].li)
  return items
    .map((li) => (typeof li === 'object' ? li : { packageId: li }))
    .map((li) => ({
      packageId: text(li.packageId),
      displayName: text(li.displayName) || text(li.packageId),
      steamWorkshopUrl: text(li.steamWorkshopUrl) || null,
      downloadUrl: text(li.downloadUrl) || null,
    }))
    .filter((d) => d.packageId)
}

两种数据统一成一个形状：

<!-- 老写法：只有一个 id -->
<li>brrainz.harmony</li>

<!-- 新写法：带元信息的对象 -->
<li>
  <packageId>brrainz.harmony</packageId>
  <displayName>Harmony</displayName>
  <steamWorkshopUrl>https://...</steamWorkshopUrl>
</li>

.map((li) => (typeof li === 'object' ? li : { packageId: li })) 把老写法"升级"成对象，之后统一处理。这个技巧叫 normalize（规范化），非常常用。

写文件：ModsConfig.xml

读和写都在这个文件里。写只有一处，非常集中。

src/host/xml.js:92-105

这一行 lower 是个 JS 花活，值得拆开 
const lower = (a) => {
  const seen = new Set()
  return (a || []).map(pid).filter((k) => k && !seen.has(k) && seen.add(k))
}

它在做"转小写 + 去重"，但用了两个技巧：

  1. new Set() 声明在函数体里，filter 的回调捕获它 —— 用闭包当"记忆"。
  2. seen.add(k) 返回 Set 本身（truthy），所以 && seen.add(k) 既能执行副作用又返回真值。整个表达式 !seen.has(k) && seen.add(k) 的语义是"没见过 → 记下来 → 返回真"。

这行代码很聪明，但不推荐模仿。清晰写法是：

const lower = (a) => {
  const seen = new Set()
  const out = []
  for (const k of a || []) {
    const v = pid(k)
    if (v && !seen.has(v)) { seen.add(v); out.push(v) }
  }
  return out
}

读别人的代码要能看懂花活，自己写时选清楚的。
