排序与诊断 387 行，做两件事：算出正确的加载顺序，以及指出现在有什么问题。算法本身是教科书内容，难的是"优先级"这套设计。

问题是什么

假设你有三个 mod：

Harmony → 声称必须在 Core 之前加载（loadBefore: ludeon.rimworld） Core → 游戏本体 Vanilla Expanded → 依赖 Harmony 问：正确顺序是什么？ 答：Harmony → Core → Vanilla Expanded

三个 mod 很简单。但真实玩家有 300 个 mod，每个都可能声明几条规则，还有社区规则库、自己的自定义规则、mod 之间的依赖关系……这就是一个有向图，要求一个合法的线性顺序。学名：拓扑排序（topological sort）。

先理解"边"的方向

代码里统一约定：一条边 A → B 意思是 A 必须在 B 之前加载。
所以 mod.loadAfter = ['brrainz.harmony'] 产生的是边 harmony → thisMod。注意方向是反的 —— 说"我在 X 之后"就是"X 在我之前"。这是初读最容易搞混的地方，代码里用 addEdge(t, key, ...) 明确表达了这一点。

第一步：建图

export function buildGraph(activeKeys, catalog, ruleStore) {
  const active = new Set(activeKeys)
  const edges = new Map()
  const tiers = new Map()
  const addEdge = (before, after, source, comment) => {
    const a = pid(before)
    const b = pid(after)
    if (!active.has(a) || !active.has(b) || a === b) return
    const k = a + '>' + b
    const prev = edges.get(k)
    if (!prev || PRIORITY[source] < PRIORITY[prev.source]) edges.set(k, { from: a, to: b, source, priority: PRIORITY[source], comment })
  }
  for (const key of active) {

    const rules = ruleStore ? ruleStore.rulesFor(key) : { loadAfter: {}, loadBefore: {}, incompatibleWith: {} }
    tiers.set(key, mod ? tierOf(mod, rules) : 3)
    if (!mod) continue

    for (const t of mod.forceLoadBefore) addEdge(key, t, 'force')
    for (const t of mod.loadAfter) addEdge(t, key, 'about')

    for (const [t, info] of Object.entries(rules.loadBefore)) addEdge(key, t, info.source === 'user' ? 'user' : 'community', info.comment)

addEdge 的三个设计决策

① 只关心已启用的 if (!active.has(a) || !active.has(b)) return —— 未启用的 mod 不参与。这个检查很重要：如果有人写了 loadAfter: ['某未启用mod']，那条边被忽略，不会导致排序死锁。而且这是每次 addEdge 都检查，所以调用方不用操心。
② 同一对 mod 只保留最强约束 if (!prev || PRIORITY[source] < PRIORITY[prev.source])：如果 a→b 这条边已经存在，只有当新来源优先级更高（数值更小）时才覆盖。
这样一条边同时被 About.xml 和社区规则要求时，会标记成 source: 'about'（更权威）。
③ 自己到自己 → 丢弃 a === b 直接 return。有些 mod 会荒唐地写 loadAfter 自己，不拦会导致后面算法出问题。

优先级表：这个项目的核心业务逻辑

const PRIORITY = { force: 0, user: 1, about: 2, community: 3, dependency: 4 }
数字来源含义翻成中文
0forceforceLoadAfter / forceLoadBefore"我必须"，作者亲自写死，永远不破
1user你自己在界面上加的规则"我要这样"，用户说了算
2aboutAbout.xml 的 loadAfter / loadBefore"我希望这样"，作者的建议
3communityRimSort 社区规则库"大家发现应该这样"，众包经验
4dependencymodDependencies"我没有它就跑不了"，但引擎会自动处理，排序上最软
为什么 dependency 优先级最低？

直觉上"依赖"应该最强 —— 没有 Harmony，别的 mod 根本跑不起来。但注意两点：

  1. 依赖关系有硬保证：游戏引擎加载时会自己解析依赖。排序只是让它在列表里看起来对。
  2. 有些 mod 会错误地声明依赖（比如声明依赖某个可选 mod），或者依赖方向和其他规则冲突。这时如果把 dependency 排最高，会强行制造矛盾。

所以设计取舍是：作者明确写的 > 用户要的 > 社区建议 > 自动推导出来的。人工声明的优先级高于机器推导的，这是很合理的原则。

分组成 tier（层）

src/host/sorter.js:26-32
function tierOf(mod, rules) {
  if (mod.key === CORE_ID) return 0
  if (mod.kind === 'expansion' || mod.key in KNOWN_EXPANSIONS) return 0
  if (rules.loadTop) return 1
  if (rules.loadBottom) return 3
  return 2
}
tier谁例子
0Core + 官方 DLC + 必须在它们之前的东西Harmony、Prepatcher、Core、Royalty…
1标了 loadTop 的框架类：XML Extensions、HugsLib
2普通 mod（绝大多数）—
3标了 loadBottom 的RocketMan（性能补丁）、各种 patch 合集
为什么要分层，而不干脆一个图全排了？

因为 tier 是"不可协商的意图"。RocketMan 声称要 loadBottom，意思是"我必须最后加载"。如果只靠边，一旦某个规则冲突，算法可能把它排到中间 —— 那就破了它的核心约定。

分层让"必须最前 / 必须最后"这类意图变成结构上的保证，而不是靠图算法碰运气。这是很实用的工程妥协：把不可协商的先固定下来，剩下的在图里慢慢排。

把 Harmony 提拔进 tier 0

看这段代码，它是整个文件里最"有想法"的部分：

src/host/sorter.js:67-78
// Promote into tier 0 anything that must load before a tier-0 mod (Harmony and
// loaders declare loadBefore Core). Iterate to a fixpoint for chains.
let changed = true
while (changed) {
  changed = false
  for (const e of edges.values()) {

      changed = true
    }
  }

逻辑：如果 X 必须在某个 tier-0 mod 之前，那 X 也是 tier 0。

Harmony 的 About.xml 里写 loadBefore: ludeon.rimworld。Core 是 tier 0，所以 Harmony 也被提拔成 tier 0。

为什么用 while (changed) 循环？

因为可能有链：A 在 B 前，B 在 Core 前。第一轮：B 被提拔（因为 Core 是 tier 0）。第二轮：A 被提拔（因为 B 现在是 tier 0）。直到一轮下来没有任何变化（fixpoint，不动点）才停。

这叫"传递闭包"的迭代算法。Python 里你会写类似 while changed: ...，一模一样。

第二步：拓扑排序

src/host/sorter.js:82-133
function topo(keys, edgeList, order) {
  const pos = new Map(keys.map((k, i) => [k, order.has(k) ? order.get(k) : 1e9 + i]))
  const indeg = new Map(keys.map((k) => [k, 0]))
  const out = new Map(keys.map((k) => [k, []]))
  const set = new Set(keys)
  let edges = edgeList.filter((e) => set.has(e.from) && set.has(e.to))
  const broken = []

  const run = () => {
    for (const k of keys) {
      indeg.set(k, 0)
      out.set(k, [])
    }
    for (const e of edges) {
      indeg.set(e.to, indeg.get(e.to) + 1)
      out.get(e.from).push(e.to)
    }
    const ready = keys.filter((k) => indeg.get(k) === 0).sort((a, b) => pos.get(a) - pos.get(b))
    const result = []
    while (ready.length) {
      const k = ready.shift()
      result.push(k)
      for (const n of out.get(k)) {
        indeg.set(n, indeg.get(n) - 1)
        if (indeg.get(n) === 0) {
          // insert keeping ready sorted by original position
          let i = 0
          while (i < ready.length && pos.get(ready[i]) <= pos.get(n)) i++
          ready.splice(i, 0, n)
        }
      }
    }
    return result
  }

这就是著名的 Kahn 算法。如果你没学过，用一句话理解：

Kahn 算法的直觉

反复做这件事：找出所有"没有前置要求"的节点，输出它，然后把它从图里删掉（也就是让它的后继少一个前置）。直到图空。

好比做菜：先做所有不需要等别的菜做好的步骤。做完一道，可能就解锁了下一道。

逐步走一遍

假设有这些边（A 必须在 B 前）：

harmony → core core → vanilla_expanded harmony → some_lib some_lib → vanilla_expanded

初始状态，indeg（入度 = 有几个前置要求）：

mod入度说明
harmony0没人要求它在别人后面 → 可以立即输出
core1要等 harmony
some_lib1要等 harmony
vanilla_expanded2要等 core 和 some_lib
  1. ready = [harmony] → 输出 harmony。harmony 的后继是 core 和 some_lib，两者入度各减 1 → 都变成 0，加入 ready。
  2. ready = [core, some_lib]（按 pos 排序决定谁先）。假设输出 core。core 的后继 vanilla_expanded 入度减 1 → 变成 1（还要等 some_lib）。
  3. ready = [some_lib] → 输出。vanilla_expanded 入度减 1 → 变成 0，加入 ready。
  4. ready = [vanilla_expanded] → 输出。

最终顺序：harmony → core → some_lib → vanilla_expanded。✓

那个 splice 循环在干什么

if (indeg.get(n) === 0) {
  // insert keeping ready sorted by original position
  let i = 0
  while (i < ready.length && pos.get(ready[i]) <= pos.get(n)) i++
  ready.splice(i, 0, n)
}

它在保持 ready 数组有序。为什么不直接 ready.push(n); ready.sort()？因为那样每次都要全排一遍。这里用插入排序的位置查找，因为数组通常很短。

为什么要保持有序？为了让"同时可选的 mod"按 pos 决定的顺序输出 —— 这就是 tie-break（平局裁决），下一节讲。

tie-break：没有约束的 mod 谁先谁后

拓扑排序只保证"该在前的在前"，但没有约束关系的 mod 之间，顺序是自由的。自由就会乱 —— 每次排序结果不同会让用户困惑。所以需要一条规则。

src/host/sorter.js:169-175
const collator = new Intl.Collator(undefined, { sensitivity: 'base', numeric: true })
const sortName = (k, catalog) => (catalog.get(k)?.name || k).trim()
/** Keys ranked by the lowest-priority criterion. */
export function tieBreakOrder(keys, catalog, tieBreak = 'name') {
  if (tieBreak !== 'name') return [...keys]
  return [...keys].sort((a, b) => collator.compare(sortName(a, catalog), sortName(b, catalog)) || collator.compare(a, b))
}
模式行为什么时候用
'name'（默认）按名字字母序。Intl.Collator 带 numeric: true，所以 "Mod 9" 排在 "Mod 10" 前面（自然序）想要稳定、可预测的结果
'current'保持当前相对顺序，只移动必须移动的已经手工排好了，只想修正错误
'rimsort'完整复刻 RimSort 的算法（另一条代码路径）和 RimSort 用户交流时保持一致
Intl.Collator 是个好东西

new Intl.Collator(undefined, { numeric: true }) 创建一个"本地化排序器"。它能正确处理中文拼音序、数字自然序、重音符号。比 a.localeCompare(b) 快得多（因为一次创建重复使用）。

文件最后那个 || collator.compare(a, b) 是兜底：名字完全相同时按 key 排，保证结果绝对确定（不会因为原数组顺序不同而不同）。

第三步：破环

拓扑排序有个前提：图里不能有环。但现实中一定会有 —— 两个 mod 互相声明要在对方之后加载，这就是矛盾。

src/host/sorter.js:118-132
let result = run()
let guard = 0
while (result.length < keys.length && guard++ < 200) {
  // Find one cycle among remaining nodes and drop its weakest edge.
  const remaining = new Set(keys.filter((k) => !result.includes(k)))
  const cycEdges = edges.filter((e) => remaining.has(e.from) && remaining.has(e.to))
  const cycle = findCycle(cycEdges, remaining)
  if (!cycle.length) break
  const weakest = cycle.reduce((w, e) => (e.priority >= w.priority ? e : w))
  broken.push({ cycle: cycle.map((e) => e.from + ' → ' + e.to), dropped: weakest })
  edges = edges.filter((e) => e !== weakest)
  result = run()
}
if (result.length < keys.length) for (const k of keys) if (!result.includes(k)) result.push(k)
return { order: result, broken }

策略：找到一个环，删掉环里优先级最低的那条边，重跑。删掉的记进 broken，最后报告给用户。

guard++ < 200防止死循环的保险。万一 findCycle 有 bug 一直找不到环，最多试 200 次就放弃。
cycle.reduce((w, e) => (e.priority >= w.priority ? e : w))在环里找 priority 数值最大的（也就是最弱的）那条边。>= 而不是 > 意味着同优先级时取后一个。Python: max(cycle, key=lambda e: e.priority)。
edges = edges.filter((e) => e !== weakest)对象引用比较，删掉那个具体的边对象。剩下的保持不可变风格。
最后一行的兜底如果 200 次还没搞定，剩下的直接按原顺序追加，保证一定返回全部 mod。宁可顺序不对，不能丢 mod。

找环的算法：DFS + 三色标记

src/host/sorter.js:135-167
function findCycle(edges, nodes) {
  const adj = new Map()
  for (const e of edges) {
    if (!adj.has(e.from)) adj.set(e.from, [])
    adj.get(e.from).push(e)
  }
  const state = new Map()
  const stack = []
  let found = null
  const dfs = (n) => {
    if (found) return
    state.set(n, 1)
    for (const e of adj.get(n) || []) {
      if (found) return
      if (state.get(e.to) === 1) {
        const i = stack.findIndex((x) => x.from === e.to)
        found = [...stack.slice(i), e]
        return
      }
      if (!state.has(e.to)) {
        stack.push(e)
        dfs(e.to)
        stack.pop()
      }
    }
    state.set(n, 2)
  }
  for (const n of nodes) {
    if (found) break
    if (!state.has(n)) dfs(n)
  }
  return found || []
}

状态标记：没记录 = 没访问过，1 = 正在访问（在当前路径上），2 = 访问完了。

关键在这一句

if (state.get(e.to) === 1) —— 如果目标节点"正在访问中"，说明我们从它出发绕了一圈又回来了，这就是环。

如果只是"访问过"（状态 2），那是正常的共享路径，不是环。这个区分是 DFS 找环的核心。Python 里你会写一模一样的递归。

然后 stack.findIndex((x) => x.from === e.to) 从栈里找出环的起点，[...stack.slice(i), e] 把环切出来。

诊断：找出问题，不只是排序

排序解决"顺序对不对"，但还有别的问题：缺依赖、版本不匹配、不兼容、mod 没装。这些归 diagnose() 管。

export function diagnose(activeKeys, catalog, ruleStore, { gameMajor, duplicates = [] } = {}) {
  const keys = activeKeys.map(pid)
  const active = new Set(keys)
  const posOf = new Map(keys.map((k, i) => [k, i]))
  const pairs = new Set()
  /** true the first time an unordered pair is seen (so each incompatibility is reported once). */
  const seenPair = (a, b) => {
    const id = a < b ? a + '|' + b : b + '|' + a
    if (pairs.has(id)) return false
    pairs.add(id)
    return true
  }
  const issues = []
  const nameOf = (k) => catalog.get(k)?.name || ruleStore?.steamByPid(k)?.name || k
  const push = (level, code, mod, message, extra = {}) => issues.push({ level, code, mod, modName: nameOf(mod), message, ...extra })

三个共享的辅助结构，每个都有明确目的：

posOfkey → 位置索引。后面判"应该在前面的却在后面"靠它。O(1) 查询，比每次 indexOf 快。
seenPair记录已报告过的"无序对"。因为不兼容是双向的：A 不兼容 B，检查 A 时报告一次，检查 B 时又会报告一次。a < b ? ... : ... 保证两种方向生成同一个 id。
push()统一的问题构造函数。自动补 modName，收尾再算 counts。所有错误都长一个形状，界面好渲染。

      { target: dk, targetName: d.displayName, steam: { pfid: steam?.pfid || pfidFromUrl, url: steam?.url || d.steamWorkshopUrl || d.downloadUrl }, fix: installed ? 'activate' : 'subscribe' })
  } else if (posOf.get(dk) > posOf.get(k)) {
    push('warning', 'order-dependency', k, `Should load after its dependency "${nameOf(dk)}"`, { target: dk, fix: 'sort' })
  }
}

这段很值得学，因为它一次检查了三种情况，而且每种都给出了可操作的修复建议：

情况levelfix 字段界面能做什么
没装error'subscribe'显示"订阅"按钮，跳到工坊页
装了但没启用error'activate'显示"启用"按钮，一键加进列表
顺序不对warning'sort'显示"排序"按钮
fix 字段是个好设计

诊断不只是"告诉你哪里错了"，而是"告诉你错在哪 + 给出修复的机器可读指令"。界面截获 fix 就知道该画什么按钮。这个思路值得抄到任何项目里。

注意最后两行：对已排序的结果再排一次，应该移动 0 个。这叫幂等性（idempotent），是排序算法的关键性质 —— 如果每次点"排序"结果都变，用户会疯掉。

这是个很好的验证思路

任何"整理/排序/格式化"类功能，都该能通过这个测试：整理两次 = 整理一次。写测试时优先加这一条。

单元测试怎么写的

看排序算法的测试，能学到怎么测纯函数：

test/sorter.test.js:1-41
import { test } from 'node:test'
import assert from 'node:assert/strict'
import { sortLoadOrder, diagnose } from '../src/host/sorter.js'

const mod = (key, extra = {}) => ({
  key,
  packageId: key,
  name: key,
  kind: key === 'ludeon.rimworld' ? 'core' : key.startsWith('ludeon.rimworld.') ? 'expansion' : 'mod',
  source: 'workshop',
  supportedVersions: ['1.6'],
  loadFolderVersions: [],
  loadAfter: [],
  loadBefore: [],
  forceLoadAfter: [],
  forceLoadBefore: [],
  incompatibleWith: [],
  modDependencies: [],
  invalid: null,
  ...extra,       // ← 关键：允许覆盖任何字段
})
const catalogOf = (...mods) => new Map(mods.map((m) => [m.key, m]))
const fakeRules = (rules = {}) => ({
  rulesFor: (k) => ({ loadAfter: {}, loadBefore: {}, incompatibleWith: {}, loadTop: null, loadBottom: null, ...(rules[k] || {}) }),
  steamByPid: () => undefined,
  steamByPfid: () => undefined,
  nvwCovers: () => false,
})

test('core first, expansions in canonical order, harmony promoted before core', () => {
  const cat = catalogOf(
    mod('ludeon.rimworld'),
    mod('ludeon.rimworld.biotech'),
    mod('ludeon.rimworld.royalty'),
    mod('brrainz.harmony', { loadBefore: ['ludeon.rimworld'] }),
    mod('some.mod'),
  )
  const r = sortLoadOrder(['some.mod', 'ludeon.rimworld.biotech', 'ludeon.rimworld', 'brrainz.harmony', 'ludeon.rimworld.royalty'], cat, fakeRules())
  assert.deepEqual(r.order, ['brrainz.harmony', 'ludeon.rimworld', 'ludeon.rimworld.royalty', 'ludeon.rimworld.biotech', 'some.mod'])
  assert.equal(r.broken.length, 0)
})

三个技巧：

  1. mod() 工厂函数 + ...extra 覆盖
    所有字段给默认值，测试时只写要改的那个：mod('brrainz.harmony', { loadBefore: [...] })。不用每次都写全 15 个字段。
  2. catalogOf(...mods) 用可变参数
    ...mods 收集所有参数成数组（就是 Python 的 *args）。调用时 catalogOf(a, b, c) 比 catalogOf([a, b, c]) 顺手。
  3. fakeRules() 造假依赖
    排序函数需要 ruleStore（里面有 rulesFor / steamByPid 等），但测试不想去下载真的规则库。所以造一个只有四个方法的假对象。这叫 mock / stub，因为 sortLoadOrder 只用到这几个方法，传个假的完全够用。
为什么这些能被测？

因为 sortLoadOrder 是纯函数：输入 keys + catalog + rules，输出 order，不读文件、不发请求、不改全局状态。纯函数最好测 —— 这也是为什么核心算法被单独放在一个文件里。

对比一下：service.js 里的东西就难测多了，因为它依赖磁盘、网络、全局 state。

整个排序流程串起来

sortLoadOrder(activeKeys, catalog, ruleStore, { tieBreak }) │ ├─ ① keys = 去重 + 转小写 ├─ ② buildGraph(keys, catalog, ruleStore) │ ├─ 遍历每个 mod，把 6 类规则转成边 │ ├─ addEdge 去重，保留最高优先级的来源 │ ├─ 官方 DLC 强制排成 Ludeon 官方顺序 │ ├─ tier 划分：Core/DLC=0, loadTop=1, 普通=2, loadBottom=3 │ └─ 迭代提拔：必须在 tier0 之前的 → tier0（直到不动点） │ ├─ ③ current = tieBreakOrder(keys, catalog, tieBreak) │ └─ 'name' → 按名字排（决定平局顺序） │ 'current' → 保持原样 │ ├─ ④ 按 tier 分四组 │ ├─ ⑤ 每组跑 topo() ← Kahn 算法 │ ├─ 算入度，找入度为 0 的 │ ├─ 逐个输出，边的目标入度 -1 │ ├─ 遇到卡住（有环）→ findCycle() → 删最弱的边 → 重跑 │ └─ 返回 { order, broken } │ ├─ ⑥ 四组结果拼起来 ├─ ⑦ 检查跨 tier 违规（报告，不强制修） └─ ⑧ 算 moved（移动了几个） return { order, moved, broken, crossTierViolations }

这个文件里有好几处"宁可结果不完美，也要返回结果"的地方。这种思路值得注意：

地方兜底策略
有环删最弱边继续，不报错，记进 broken
200 次还解不开环剩下的按原顺序追加，不丢 mod
跨 tier 违规只报告不修（因为 tier 是硬意图，修了更糟）

这一页的收获

你看到了一个完整的"把现实世界的模糊需求变成确定算法"的过程：定义边的方向和优先级 → 分层固定硬意图 → 拓扑排序 → 破环兜底 → 平局裁决保证幂等。

真正的技术含量不在于会不会写拓扑排序，而在于这套优先级设计。哪条规则该压过哪条，冲突时牺牲什么 —— 这才是这个项目 387 行代码背后的思考。
